{# upgrade/confirm.html - the upgrade confirmation page of the upgrade capture portal. Why this file exists: An upgrade writes firmware and reboots a device. The operator must not reach that action with one press. FR-033 and FR-034 ask for a typed word, and the customer asked for "a box the operator must type a word into before a shaded-out begin button unlocks". This page holds that box and that button, and it holds nothing else that can start work. The last read of the plan sits on the same page, so the operator reads the count of devices and the warnings before the word unlocks the button. Why the begin button starts disabled: The disabled attribute sits in the markup, not in a script. A browser that fails to load portal.js therefore leaves the button locked. A page that started unlocked and relied on a script to lock it would start an upgrade after a script error. Why one variable holds the word: contracts/ui-testids.md line 111, contracts/http-api.md line 226, FR-033, and task T152 all name the word CONFIRM. The word sits in one Jinja variable and reaches the visible text and the data-confirm-word attribute from there, so a change of the word costs one line. portal.js reads the attribute and never holds the word itself. Why the page holds no script: The content security policy is 'self' only. The policy blocks an inline script and blocks the style attribute. Every behavior lives in portal.js. Why the links hold a literal path: contracts/http-api.md fixes every public path of this portal. The blueprint endpoint names are not fixed, so a url_for call against an endpoint name would raise while this page renders. The contract with portal.js: The input carries data-confirm-word and data-confirm-target. portal.js enables the named button only when the typed text equals the word exactly. The button carries data-run-id and data-progress-url. portal.js sends POST /api/runs//start with the typed text in the confirm field, then moves the browser to the progress path.

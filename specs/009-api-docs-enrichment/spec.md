# Feature Specification: Mist API Documentation Enrichment

**Feature Branch**: `009-api-docs-enrichment`  
**Created**: 2026-03-06  
**Status**: Draft  
**Input**: User description: "Fill out all the 'To be enriched by AI agent' placeholder sections in documentation/api/ endpoint files with usage context, gotchas, related endpoints, and MistHelper notes for every Mist API endpoint"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AI Agent Gets Actionable Endpoint Guidance (Priority: P1)

An AI coding agent is writing MistHelper code that calls a Mist API endpoint. The agent reads the endpoint's markdown file and finds not just the raw HTTP/schema data (already generated by Feature 008) but also practical guidance: when to use this endpoint, what pitfalls to avoid, and which related endpoints are commonly called in the same workflow. This lets the agent write correct, idiomatic code on the first attempt instead of discovering edge cases through trial and error.

**Why this priority**: The entire purpose of the documentation is to make AI agents more effective at writing Mist API code. Without enrichment, the files contain only raw schema data that an agent could get from the OpenAPI spec directly. Enrichment adds the domain knowledge that makes these files uniquely valuable.

**Independent Test**: Open any 5 enriched endpoint files. Each file's Usage Context section should contain at least one concrete use case. Each Gotchas section should contain at least one pitfall or explicitly state "No known gotchas." Each Related Endpoints section should link to at least one other endpoint file using a correct relative path that resolves to an existing file.

**Acceptance Scenarios**:

1. **Given** an enriched endpoint file for `listOrgSites`, **When** an AI agent reads the Usage Context section, **Then** the agent finds at least one concrete scenario describing when and why to call this endpoint
2. **Given** an enriched endpoint file for `createOrgSite`, **When** an AI agent reads the Gotchas section, **Then** the agent finds specific pitfalls (such as required fields not obvious from the schema) or an explicit "No known gotchas" statement
3. **Given** an enriched endpoint file for `listSiteDevices`, **When** an AI agent reads the Related Endpoints section, **Then** each cross-reference is a relative markdown link that resolves to an existing file in the documentation/api/ directory tree

### User Story 2 - MistHelper Developer Finds Menu-to-API Mapping (Priority: P2)

A developer maintaining MistHelper needs to understand which menu operations call which API endpoints. The developer opens an endpoint file and finds a MistHelper Notes section that identifies the relevant menu operation number(s) and any special handling (such as passing `type=all` for device listing). For endpoints not used by MistHelper, the section clearly states "Not currently used by MistHelper."

**Why this priority**: MistHelper-specific notes require scanning the ~28K-line MistHelper.py codebase to find where each API function is called. This is the most labor-intensive enrichment section but provides unique value that cannot be found anywhere else.

**Independent Test**: For 5 endpoints known to be used by MistHelper (e.g., `listOrgSites`, `listSiteDevices`, `getOrgInventory`), verify the MistHelper Notes section references the correct menu operation number. For 5 endpoints known not to be used by MistHelper, verify the section states "Not currently used by MistHelper."

**Acceptance Scenarios**:

1. **Given** an enriched file for an endpoint used by MistHelper, **When** a developer reads the MistHelper Notes section, **Then** the section identifies the menu operation number and describes any special parameter handling
2. **Given** an enriched file for an endpoint not used by MistHelper, **When** a developer reads the MistHelper Notes section, **Then** the section states "Not currently used by MistHelper"

### User Story 3 - Complete Enrichment Across All Categories (Priority: P3)

All 1,013 endpoint files across all 8 categories have their 4 placeholder sections replaced with real content. No file contains the placeholder text "*To be enriched by AI agent.*" after the enrichment process is complete. The enrichment follows the ascending batch order defined in ENRICHMENT_GUIDE.md (admins first, orgs last).

**Why this priority**: Full coverage is ultimately required, but partial enrichment (even just the pilot batch of admins/) already delivers value. This story ensures completeness after the core enrichment logic is proven.

**Independent Test**: Run a grep across all 1,013 endpoint files for the string "To be enriched by AI agent." The result count should be zero. Count the total enriched files per category and verify they match the expected counts (admins: 13, self: 18, installer: 23, constants: 27, msps: 50, utilities: 103, sites: 330, orgs: 449).

**Acceptance Scenarios**:

1. **Given** the complete documentation/api/ directory, **When** searching for "To be enriched by AI agent" across all files, **Then** zero matches are found
2. **Given** an enriched file in any category, **When** inspecting the four enrichment sections, **Then** none contain placeholder text and all contain substantive content following the templates defined in ENRICHMENT_GUIDE.md

### Edge Cases

- What happens when an endpoint has no obvious use cases (e.g., internal or rarely-used admin endpoints)? Usage Context should still describe the endpoint's purpose derived from its HTTP method, path, and description, even if use cases are uncommon.
- What happens when an endpoint has no known gotchas? The Gotchas section should explicitly state "No known gotchas" rather than being left empty or containing generic filler.
- What happens when an endpoint is deprecated? The enrichment should note that the endpoint is deprecated in the Usage Context and recommend the replacement endpoint if one exists.
- What happens when related endpoints are in a different category directory? Cross-reference links must use correct relative paths with `../` prefix (e.g., `../orgs/GET_orgs_org_id.md` from a `sites/` file).
- What happens when MistHelper uses an endpoint indirectly (e.g., via mistapi SDK calls that are not obvious)? The MistHelper Notes section should document the actual mistapi function call pattern found in MistHelper.py.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Each enriched endpoint file MUST have its Usage Context section replaced with at least one concrete use case describing when and why to call this endpoint
- **FR-002**: Each enriched endpoint file MUST have its Gotchas section replaced with at least one specific pitfall or an explicit "No known gotchas" statement. Gotchas SHOULD be derived from structural inference (parameters, required fields, pagination, deprecation) AND from research across all available sources including web resources (Mist API documentation, Juniper knowledge base, community forums). "No known gotchas" SHOULD only be used for trivially simple endpoints with no parameters and no request body
- **FR-003**: Each enriched endpoint file MUST have its Related Endpoints section replaced with relative markdown links covering the full relationship graph: CRUD siblings on the same resource, parent resource endpoint, sub-resource endpoints, and cross-scope equivalents (e.g., org-level and site-level versions). All links MUST use correct relative paths that resolve to existing files
- **FR-004**: Each enriched endpoint file MUST have its MistHelper Notes section replaced with either the relevant menu operation number(s) and special handling notes, or a clear "Not currently used by MistHelper" statement
- **FR-005**: Enrichment MUST proceed in ascending batch order by category size as defined in ENRICHMENT_GUIDE.md: admins (13), self (18), installer (23), constants (27), msps (50), utilities (103), sites (330), orgs (449). Within large categories, git commits SHOULD occur every ~50 files to create recovery checkpoints
- **FR-006**: All cross-reference links in Related Endpoints sections MUST use correct relative paths (e.g., `../orgs/GET_orgs_org_id_sites.md` for cross-category references, `GET_sites_site_id.md` for same-category references) and MUST resolve to existing files
- **FR-007**: Enrichment content MUST be factually accurate and consistent with the OpenAPI spec data already present in each file (HTTP method, path, parameters, schemas). The AI agent SHOULD research all available sources — OpenAPI spec, MistHelper.py source, agents.md patterns, and web resources (Mist API docs, Juniper knowledge base, community forums) — to maximize content quality and accuracy
- **FR-008**: No enriched file MUST contain the placeholder text "*To be enriched by AI agent.*" after enrichment is complete
- **FR-009**: Deprecated endpoints MUST include a note in Usage Context acknowledging the deprecation and recommending a replacement endpoint if one is identifiable from the API spec

### Key Entities

- **Endpoint File**: A markdown file in documentation/api/{category}/ representing one API operation. Contains raw OpenAPI data (from Feature 008) plus 4 enrichment sections to be filled.
- **Category**: One of 8 directories (admins, self, installer, constants, msps, utilities, sites, orgs) grouping endpoint files by the first word of their OpenAPI tag.
- **Enrichment Section**: One of 4 placeholder sections in each endpoint file: Usage Context, Gotchas, Related Endpoints, MistHelper Notes.
- **Batch**: A group of endpoint files processed together, corresponding to one category directory.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All 1,013 endpoint files contain enriched content with zero remaining placeholder text ("To be enriched by AI agent") across all 4,052 enrichment sections
- **SC-002**: 100% of cross-reference links in Related Endpoints sections resolve to existing files when validated programmatically
- **SC-003**: For endpoints used by MistHelper, 100% of MistHelper Notes sections correctly identify the menu operation number, verified by cross-referencing against MistHelper.py source code
- **SC-004**: Each enriched file passes all 7 items in the Quality Checklist defined in ENRICHMENT_GUIDE.md

## Clarifications

### Session 2026-03-06

- Q: How should enrichment content be generated — script-derived, AI-agent enriched, or hybrid? → A: AI-agent enriched, processing files category by category
- Q: What is the commit/checkpoint boundary during enrichment? → A: Commit per batch of ~50 files, checkpointing more frequently within large categories (sites, orgs)
- Q: How deeply should Related Endpoints cross-references go? → A: Full graph — CRUD siblings, parent resource, sub-resources, and cross-scope equivalents (e.g., site-level and org-level versions)
- Q: How should Gotchas be derived for endpoints without first-hand usage knowledge? → A: Structural inference from parameters, required fields, pagination, deprecation, and common patterns. Additionally, research all available sources including web resources (Mist API docs, community forums, Juniper knowledge base). Reserve "No known gotchas" only for trivially simple endpoints.

## Assumptions

- The raw endpoint files generated by Feature 008 are complete and correct; this feature only modifies the 4 enrichment sections per file
- The ENRICHMENT_GUIDE.md quality checklist and section templates are the authoritative reference for enrichment content format
- MistHelper.py source code is the authoritative source for determining which endpoints are used by MistHelper and which menu operations call them
- The OpenAPI spec (documentation/mist-api-openapi31json.json) is the authoritative source for verifying factual accuracy of enrichment content
- Endpoints that are not currently used by MistHelper should be documented as such rather than speculating about future use
- Enrichment is performed by an AI agent reading each endpoint file and writing domain-knowledge content, not by an algorithmic script generating generic text
- The AI agent should leverage all available information sources: OpenAPI spec, MistHelper.py source, agents.md, ENRICHMENT_GUIDE.md, and web resources (Mist API documentation, Juniper knowledge base, community forums, GitHub repositories)

## Scope Boundaries

**In scope**:
- Replacing all 4 placeholder sections in all 1,013 endpoint files
- Cross-referencing MistHelper.py to identify menu-to-API mappings
- Validating link integrity and content quality

**Out of scope**:
- Modifying any non-enrichment sections (HTTP, Parameters, Request Body, Response, Errors, Pagination, Rate Limiting, mistapi SDK)
- Changing the file structure, naming, or directory layout
- Adding new endpoint files or modifying INDEX.md
- Updating the OpenAPI spec source files
- Re-running the Phase 1 generation script

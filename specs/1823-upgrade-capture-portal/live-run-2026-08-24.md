## 3. The five defects that only a real run could find

Every one of these passed the whole test suite. Four of the five share one cause:
a stand-in answered a simpler shape than the library or the module really
answers, so every reader passed its own test and failed the cloud.

| Defect | Where | What an operator met |
| --- | --- | --- |
| 1. The privilege list reads as absent | `runtime/identity.py session_privileges` tested `isinstance(value, list)`. `mistapi` 0.63 answers a `Privileges` object, which iterates and holds no length | The organization picker showed "This sign-in reaches no organization" for a token that reaches one. The journey stopped at the first page |
| 2. The token sign-in never signs in | `app/routes/auth.py default_token_session` built the session and returned it | The cloud never named the scope, so the picker stayed empty even after defect 1 |
| 3. The entry point reads no `.env` | `wsgi_capture.py` never loaded the file. `MistHelper.py` loads it, so menu 238 works and Gunicorn does not | The sign-in page said "This server holds no API token variable" while `.env` named one. The container runs `gunicorn wsgi_capture:app`, so the token mode was unavailable there too |
| 4. The inventory read drops the session | `app/routes/select.py read_inventory` called the device reader with two identifiers. The reader names `session` first | `GET /select/site/<id>` answered 500 for every real site |
| 5. The inventory answer reads as empty | `as_records` knew a list and a mapping. The device module answers a `DeviceRead` object that carries the rows under `records` | The page rendered and showed no device for a site that holds eight |

A sixth finding is smaller and real. The inventory endpoint names the device
state `connected` and carries a boolean. The table reads `status`, so all eight
devices read `unknown` while all eight were connected. `with_status_word` now
turns the boolean into a word, and the page reads `connected` for each one.

`tests/unit/upgrade_portal/test_privilege_shapes.py` holds 15 tests that copy the
shapes the library and the device module really answer with. Every one of the six
findings fails at least one of those tests against the old code.

## 4. The one step that still fails, and why

The capture wrote its backup file and did not verify. `capture/store.py` sets
`verified` only when the database holds the document and the read-back matches.

**Correction of 2026-08-24, later the same day.** The first version of this
section blamed issue #1824 and the `MISTHELPER_STANDALONE` workaround. That was
only half the cause, and the other half was ours.

`capture/store.py:637 bootstrap_storage` states that "the portal calls this
function on every start". No caller existed anywhere in `src`, in `tests`, in
`MistHelper.py`, or in `wsgi_capture.py`. The collections therefore never
appeared. A capture wrote through the router, which answers a success envelope
after a file fallback, and the read-back reported `document_absent`.

Commit `b276be78` adds the call. The portal now reports 3 collections and 7
indexes at start. The write still does not land, and issue #2002 holds the
evidence and everything that is ruled out.

The handoff advice compounds it. `store.py:506` returns `None` for the database
whenever `standalone_mode` is set, so the `MISTHELPER_STANDALONE=true` that
section 4.2 of `HANDOFF.md` prescribes guarantees that no capture can verify.

## 5. Warning: the upgrade ran, and it caused an outage

The read half of this record ends above. The write half ran later the same day,
with the authorization of the operator and one stated constraint: reboot at
midnight, or do not reboot at all.

The no-reboot choice was taken. Two calls went out through
`src/firmware/upgrade_service.py`, each with `reboot: false`, and the cloud
accepted both with status 200.

| Device | From | To | Outcome |
| --- | --- | --- | --- |
| SRX-1500, a Junos gateway | 23.4R2-S5.5 | 24.2R2-S5.3 | Installed with no reboot. The choice held |
| Morrison-Switch, an EX4100-F-12P | 25.2R1-S2.3 | 25.4R1-S2.3 | Installed and rebooted. The choice did not hold |

The six access points were excluded on purpose, because the cloud reboots an
access point on its own and neither of the two choices could be honored for one.

The switch rebooted four seconds after it installed the image. It carries power
over Ethernet for all six access points, so every one of them dropped with it.

| Time | Event |
| --- | --- |
| 13:59:33 | `SW_UPGRADED` from 25.2R1-S2.3 to 25.4R1-S2.3 |
| 13:59:37 | `SW_REBOOTING` to the pending version |
| 14:01:08 | Six access points report `AP_DISCONNECTED` |
| 14:04:51 | The switch reports a cold start |
| 14:06:48 | The access points reconnect |
| 14:07:12 | Office AP reports `AP_RESTARTED`, reason `power_cycle` |

The site lost service for about six minutes. Issue #2007 holds the whole record
and the cause, which is that this module reaches only the site batch endpoint
and never the per-device endpoint that the request body schema documents for one
device.

### 5.1 Four signals reported success while the reboot happened

This is the part to read before you write a verifier.

| Signal | What it said | The truth |
| --- | --- | --- |
| `getSiteDeviceUpgrade.status` | `completed` | The gateway was still installing 31 minutes later |
| `listSiteDevicesStats.version` | The old version for about ten minutes | Already the new one |
| `listSiteDevicesStats.uptime` | The same number in two reads 15 minutes apart | Reset by the reboot |
| `read_upgrade_status.reboot_in_progress` | Empty throughout | A reboot was under way |

Two signals told the truth: `searchSiteDeviceEvents`, and the device field
`fwupdate_stat.progress_brief`.

The settle gate reads `reboot_in_progress`. That field stayed empty through a
real reboot, so the gate rests on a signal that this run watched fail.

## 7. How to repeat this run

```powershell
$env:MISTHELPER_STANDALONE = "true"
$env:REDIS_HOST = "127.0.0.1"
$env:REDIS_PASSWORD = "misthelper"
.\.venv\Scripts\python.exe -m waitress --listen=127.0.0.1:8056 --threads=4 wsgi_capture:app
```

Open `http://127.0.0.1:8056/`, choose the token mode, and type any work address.
The token names the organization, so the address only labels the log record.

### 2.1 Warning: the portal can report a stopped device while that device writes firmware

An operator who reads the word stopped can cut power to a switch. A switch that
loses power while it writes firmware does not start again. Both defects below
produce that reading.

#### Defect 1. A MAC address with dash separators never matches the guard. Verified

```
src/firmware/upgrade_service.py:801  frozenset(str(value).replace(":", "").replace("-", "").lower() ...)
src/firmware/upgrade_service.py:842  already = tuple(mac for mac in macs if mac.replace(":", "").lower() in writing)
src/firmware/upgrade_service.py:843  stopped = tuple(mac for mac in macs if mac.replace(":", "").lower() not in writing)
```

Line 801 removes the colon and the dash. Lines 842 and 843 remove the colon
alone. A MAC address written `aa-bb-cc-dd-ee-ff` therefore never matches a set
member. The device always falls into `stopped`.

The message at `:820` then states that no device was writing firmware.

**Fix**: give the three lines one shared normalizing function.

#### Defect 2. Every session smart router reports as stopped. Verified

The chain runs through five files and each step is correct on its own.

| Step | Line | What happens |
| --- | --- | --- |
| 1 | `upgrade/options.py:416-418` | A session smart router always uses the organization scope |
| 2 | `firmware/upgrade_service.py:910-911` | At that scope the status read calls `listOrgDevicesStats`, which returns device statistics and not an upgrade job |
| 3 | `firmware/upgrade_service.py:936` | The list becomes the mapping `{"devices": [...]}` |
| 4 | `firmware/upgrade_service.py:793-801` | That mapping holds neither `reboot_in_progress` nor `targets`, so the reader returns an empty set |
| 5 | `firmware/upgrade_service.py:841-843` | An empty set puts every MAC address into `stopped` |

The operator then reads that the cloud stopped every device and that no device
was writing firmware. The code cannot know either fact at the organization
scope.

Step 1 and step 2 are both deliberate. `data-model.md:281-289` fixes the scope,
and the seam must never call `getOrgSsrUpgrade`, because the installed SDK
builds the cancel path inside that function. The defect is that the reader
treats an unknown state as a known safe state.

**Fix**: make the reader answer "unknown" instead of an empty set when the
payload holds no upgrade job. Report the devices as unknown, never as stopped.
`upgrade/stop.py:204` must not set `status_known` to true for that answer.

### 2.2 High

#### Defect 3. The takeover that needs the typed word CONFIRM cannot run in production. Verified

```
src/upgrade_portal/runtime/lock.py:114  LOCK_TTL_SECONDS: Final[int] = 300
src/upgrade_portal/runtime/lock.py:119  COOLDOWN_SECONDS: Final[int] = 300
```

The lease and the cooldown are the same length. A refresh writes the timestamp
and the 300-second expiry together, at `:1076-1080`. The test for a quiet holder
is an age of 300 seconds or more, at `:636`.

The key therefore dies at the same moment that its holder turns quiet. A second
operator finds no key. The plain acquire at `:903` succeeds and returns
`ACQUIRED` at `:1028`.

The whole takeover branch at `:986-999` needs a key that still lives and that
already turned quiet. No such moment exists. The typed word `CONFIRM`, the
takeover audit record, and the audit line are all unreachable. The same defect
disables the resume guard at `:958-964`, which asks for the typed word
`continue`.

This defeats two of the five closed decisions about identity and locking.

**Fix**: make the cooldown strictly shorter than the lease. A cooldown of 300
seconds needs a lease of more than 300 seconds. The heartbeat runs every 60
seconds at `:124`, so a lease of 420 seconds keeps seven heartbeats of margin
and leaves a 120-second window in which the takeover can run.

#### Defect 4. An open endpoint drives two store writes for each call. Verified

`GET /readyz` at `src/upgrade_portal/app/factory.py:467` carries no session
guard. The portal registers no request throttle of any kind. The only global
hook is the optional address allow list at `app/security.py:152`, and that hook
registers nothing when the list is empty, which is the shipped default. The
cross-site request forgery check covers a state-changing request alone, so a
`GET` passes it.

Each call then performs real work:

```
factory.py:346-353  create the collection when absent, insert a document, read it back
factory.py:371-373  write a key into the lock store, read it back
```

Any client that reaches the port drives one document store write and one lock
store write for each request. The writes use one fixed key each, so the stored
data never grows. The load on both stores does grow.

**Fix**: bind the readiness answer to a short cache, or move the write probe
behind the address allow list. Do not remove the write probe. It exists because
a read-only replica answers a ping and refuses every write, and the site lock
would then fail for every operator while the probe reported the store ready.

## 7. Addendum. Defect 23, the start that nothing could unlock

Defect 22 gave the options page a device row. The journey then stopped one page
later, at the confirmation page.

### 7.1 Warning: no line wrote the field that FR-035 reads. Verified

Ten places read `pre_capture_id`. The route guard, the confirmation page, the
run status view, and the run driver all read it. No line in `src/` wrote it.

FR-035 refuses a start until the record names a verified pre-check. A field that
no writer sets is therefore a permanent refusal. Every operator who took a
pre-check capture and typed the word `CONFIRM` read `409 pre_capture_missing`,
and the page gave the cure of a capture they had already taken.

### 7.2 The fix

`app/routes/capture.py:263 record_status` is the one guarded writer that learns a
capture reached the verified state. The fix joins the capture to its run from
that one place.

| Line | What it does |
| --- | --- |
| `capture.py:285` | `pre_check_run` answers the run key of a pre-role capture, and an empty string for a post-role capture |
| `capture.py:304` | `attach_pre_capture` reads the run through `run_store()` and writes the field |
| `capture.py:325` | The write itself, which FR-035 then reads |

The post half stays out. `upgrade/driver.py` writes `post_capture_id` when the
upgrade ends, and a second writer here would race that one.

The join reaches the run store through the public `current_app.app_context()`
call, because the capture work runs on a worker thread with no request context.

Commit `b2bd098` holds the fix. `tests/contract/upgrade_portal/test_capture_attach.py`
holds eight tests, and one of them drives the whole journey: capture the site,
then send the upgrade.

### 7.3 Related, and deliberately left alone

`app/routes/capture.py:561 build_job` hard-codes the first ordinal, so a post
capture of one run takes the same `capture_id` as the pre capture of that run.
The repeat capture then overwrites the pre-check. Section 2.6 already records
this. It is a separate defect with a separate fix, and this change does not
touch it.

## 8. Addendum. Defect 24, the portal that forgot every run at once

### 8.1 Warning: every write claimed success and every read denied the run. Verified

`capture/store.connect_database()` answers None when no ArangoDB server answers.
`DocumentRunStore.write_run` still reported success in that state, because it
wrote the comma-separated value backup and that write worked.

The read side has no such fallback. `read_run` asked the database, the database
was absent, and the read answered None.

The portal therefore created a run, answered `201` with a run key, and then
answered `404 run_not_found` for every later call that carried that key. The
options page, the confirmation page, the start, the status poll, and the stop
control all failed together, and no log line reported a fault.

This is the defect that a standalone workstation and a container with no
database both meet. It is not a test defect.

### 8.2 The fix

`app/wiring.py:87-89` holds a bounded process-local mirror behind one lock.

| Line | What it holds |
| --- | --- |
| `wiring.py:87` | `_MIRROR`, the runs of this process, oldest first |
| `wiring.py:88` | `_MIRROR_GUARD`, because the driver thread writes while the poll reads |
| `wiring.py:89` | `MIRROR_LIMIT`, so a portal that runs for weeks does not grow without bound |
| `wiring.py:92` | `mirror_run`, which only a durable write reaches |
| `wiring.py:112` | `mirrored_run`, the fallback of the single read |
| `wiring.py:126` | `mirrored_site_runs`, the fallback of the site list |

The database always answers first. The mirror answers only when the database
holds nothing. A durable write is the one path into the mirror, so a failed
write can never leave a record that a later read presents as saved.

Commit `506250b` holds the fix.

### 8.3 What the mirror is not

The mirror is one process. Two workers do not share it, and a restart empties
it. It keeps one operator's journey whole while the database is absent. It is
not a database, and it does not close issue #1824.

the bulk control a first entry with an empty value, and
`assets/static/js/portal.js:1105 collectUpgradeTargets` keeps a row only when

rule: an empty version means the operator does not want to upgrade that device.

An operator who opens the options page and presses save without choosing a

The operator reads a site that never changed as an upgraded site. That is the
same class of misreading that the lost-lock decision exists to prevent.

The portal's own log named the cause in four lines:


### 9.4 FR-037 is not a defect

The browser tests meet `409 upgrade_already_running` often. That answer is
correct, and it names the live run in `details.run_id`, so the page can open it.

`stopping` to `stopped`. A test that tried to clear a site by stopping its run
would therefore wait for a driver that no test runs.

The harness follows the refusal's own cure: it opens the run the refusal names.
A future reader should not read that 409 as a bug.

## 10. Addendum. Defects 26 and 27, found by looking at the portal

Defect 25 was found by driving the browser journey with a test. These two were
found by opening the portal and reading the page with a person's eyes. The 129
browser tests passed while both defects stood.

The reason is the same for both. Rule 4 of `contracts/ui-testids.md` states that
a test selects by `data-testid` only. That rule keeps a test stable, and it also
means a test never reads what the operator sees. A control that carries the
right attribute and paints as an empty box passes. A page that renders no link
at all also passes, because no test asked for the link.

### 10.1 Warning: the policy blocked every control graphic of the portal. Verified

`app/security.py:30` set the image rule to `img-src 'self'`.

Bootstrap does not ship the graphic of a control as a file. It draws the caret of
a selection list, the dot of a radio control, the tick of a checkbox, and the
knob of a switch as an inline SVG image, and each one arrives as a `data:` URI
inside the stylesheet. The rule above names no scheme, so the browser blocked
every one of them.

The count is measured, not estimated. `bootstrap.min.css` holds 23 `url(data:`
rules across 21 selectors. The three portal stylesheets hold none.

The blocked list includes `.form-check-input:checked[type=radio]`,
`.form-check-input:checked[type=checkbox]`, `.form-select`, and both states of
`.form-switch .form-check-input`.

That list is the whole control set of this feature. The customer asked for "a
bubble menu list of selectable options", and the bubble is a radio. An operator
who chose a firmware version saw no dot appear. A switch painted as an empty
pill in both states, so it read as one dead control and not as a setting.

The browser stated the fault plainly, and no test read it:

```text
img-src blocked data
```

### 10.2 Warning: the site page held no forward step. Verified

`select/inventory.html:95` renders the link to the capture page inside
`{% if capture_link %}`. Line 62 of the same file derives that name:

```jinja
{% set capture_link = capture_url | default('', true) %}
```

No Python anywhere set `capture_url`. The value was therefore always empty, the
test was always false, and the link never rendered.

`contracts/ui-testids.md:74` names `site-capture-link` as "The link from the
inventory view to the capture page". A search of the whole `tests` folder for
that identifier returned nothing, so no test ever asked for it.

The destination worked. Two requests against the running portal show the shape
of the defect exactly:

```text
/captures/new?site_id=<site>   200   capture-start-button present, site-capture-link absent
/select/site/<site>            200   site-capture-link absent
```

An operator could sign in, pick an organization, pick a site, and read the device
table. At that point the journey stopped. Every later step of the feature was
reachable by typed address only.

### 10.3 The fix

| File | What changed |
| --- | --- |
| `app/security.py:34` | The image rule now reads `img-src 'self' data:` |
| `app/routes/select.py:63` | `NEW_CAPTURE_SEGMENT`, `CAPTURE_PAGE_PATH`, and `SITE_ARGUMENT` |
| `app/routes/select.py` | `capture_page_url`, which escapes the site into the query |
| `app/routes/select.py:1181` | The inventory render passes `capture_url` |

The scheme reaches the image rule alone. It stays out of `script-src` and
`object-src`, where an injected string could then run as code.

The capture page needs no new route. `app/routes/capture.py:975` already reads
the site from the query argument, and its docstring at `:922` already states that
an operator reaches the page from a link. The design intent was in the code. The
link was missing.

### 10.4 A contract test held the first defect in place

`tests/contract/upgrade_portal/test_security.py` banned `data:` everywhere in the
policy, through one parametrized list of forbidden sources. The correct fix

The ban was right in spirit and too wide in scope. A `data:` source in

This is worth recording on its own. A test that over-constrains does not merely

## 11. Addendum. Defect 28, the capture that verifies and cannot be read

A third by-eye drive found this one. It is a defect of the browser harness and
not of the shipped portal, and the section states that plainly. The harm is real
anyway, because the harness told every reader that a broken endpoint worked.

### 11.1 Warning: the read endpoint answered 500 for a verified capture. Verified

An operator opened `/captures/new?site_id=e2e-site-0001`, chose tier 2, and
pressed the start control. The capture ran to the end. The result panel showed
the verified badge, and the browser console showed this:

```
Failed to load resource: the server responded with a status of 500
The stored size read failed. server_error 500
```

The stored size then read `0` for the rest of the session.

The timing invited a race reading, because the first 500 arrived 45 milliseconds
after the start and the store write landed 688 milliseconds later. A second read,
taken from inside the page after the capture reached the verified state, refuted
that reading:

| Endpoint | Status | Body |
| --- | --- | --- |
| `GET /api/captures/<capture_id>` | 500 | `{"error":{"code":"server_error",...}}` |
| `GET /api/captures/<capture_id>/status` | 200 | `"state":"verified"`, `"percent":100` |

A capture that the portal calls verified could not be read back.

### 11.2 The cause. One settings key, two readers, two shapes

Two route modules read the one Flask settings key `CAPTURE_LOADER`:

| Module | Constant | Line |
| --- | --- | --- |
| `app/routes/capture.py` | `LOADER_KEY` | 69 |
| `app/routes/review.py` | `CAPTURE_LOADER_KEY` | 196 |

They accept different shapes. `review.py:438` accepts the record of the store
**and** a bare document, and its docstring states that it does so to keep a test
stand-in small. `capture.py:895` accepts the record alone, because it reads
`comparable` to decide whether the document may leave the portal.

The browser stand-in answered a bare document. `capture.py` therefore refused
every read, `refusal_for` read an empty reason, and an empty reason is not a key
of `REFUSAL_STATUS`, which holds `capture_not_found` and `capture_not_verified`
alone. The route fell through to the 500.

The shipped portal is not affected. `capture.py` resolves `store.load_capture`
and `review.py` resolves `store.load_capture_for_comparison`, and both return a
`CaptureLoad` record. The fault lives in the stand-in of
`tests/e2e/upgrade_portal/conftest.py`, whose own docstring claimed a shape that
`read_capture` accepts. That claim was false.

### 11.3 The fix, and the fix that was rejected

The quick fix is to make `capture.py` accept a bare document, the way `review.py`
does. That fix is dangerous. A bare document carries no `comparable` flag, so the
route would hand out a half-written capture. `store.load_capture_for_comparison`
exists to stop exactly that, and its docstring says so.

The stand-in is the wrong part, so the stand-in is the part that changed.
`conftest.py` now answers a frozen `StandInCaptureLoad` record with the three
names `capture`, `comparable`, and `reason`. One assignment still serves both
route modules, because both read the same key string.

Do not "fix" the other empty-reason path. `store.py:68` names
`database_unreachable`, that reason is also absent from `REFUSAL_STATUS`, and it
also produces a 500. That is deliberate and is held by
`tests/contract/upgrade_portal/test_capture_read.py:432`, whose reason states
that a 404 would tell an operator that the capture is gone, and the operator
would then run the whole capture again for nothing.

### 11.4 Why 132 browser tests passed

No browser test called `GET /api/captures/<capture_id>`. The endpoint carried no
coverage at all in that suite, so the suite could not see the fault.

`tests/e2e/upgrade_portal/test_capture.py` now holds `TestStoredCaptureRead`,
which reads a stored capture key from the history page and then reads the
capture back. Both tests fail against the reverted stand-in with the same 500
that the browser showed, and both pass after the fix.

| --- | --- | --- |
| `tests/e2e/upgrade_portal` | 132 passed, 0 skipped | 134 passed, 0 skipped |

## 12. Addendum. Defects 29 and 30, found by looking at the colors

A request to make the brand theme dark uncovered these two. Both are older than
that request. Both are one defect in two places, and neither one is visible in
the stylesheet. Every rule is present. Every custom property holds the right
value. The browser paints a different color anyway.

### 12.1 Warning: every link of the header ignored its own color. Verified

The header of the dark theme is a solid brand fill. The brand text and the
navigation links painted pale pink on that fill instead of white. A read of the
live page named the fault:

| Element | Painted | Token | The token names |
| --- | --- | --- | --- |
| `.portal-brand` | `rgb(255, 138, 196)` | `--portal-header-text` | `rgb(255, 255, 255)` |
| `[data-testid="nav-sites"]` | `rgb(255, 138, 196)` | `--portal-header-link` | `rgb(255, 230, 242)` |

`rgb(255, 138, 196)` is `#ff8ac4`, which is `--portal-link`. Every header link
took the page link color.

### 12.2 Warning: a link drawn as a button kept the color and the rule of a link

The portal draws some controls as a link, because the control moves the operator
to another page. The markup is `<a class="portal-button portal-button-primary">`.
Such a link painted `rgb(255, 138, 196)` on the brand fill `rgb(226, 0, 116)`,
and it kept the underline that a browser draws under a link. The button rule
names the color `--portal-on-accent`, which is white.

Five pages of the portal carry such a link. `/history` carries two,
`/select/site` carries one, and `/select/site/<site_id>` carries one.

### 12.3 The cause. One selector with two names beats one selector with one name

Section 5 of `portal.css` colors a link for the whole page:

```css
.portal-shell a { color: var(--portal-link); }
```

That selector names one class and one element. A rule that names one class alone
loses to it, whatever the order in the file. Three rules named one class alone:

| Rule | Names | Result |
| --- | --- | --- |
| `.portal-brand` | one class | loses |
| `.portal-nav a` | one class, one element, and stands earlier in the file | loses |
| `.portal-button-primary` | one class | loses |

The active tab is the one header rule that always won. `.portal-nav a.is-active`
names two classes and one element, so it outranks the section 5 rule on its own.

The fix adds the `.portal-header` class to each header rule and the
`.portal-shell` class to each button rule. Each rule then names one more class
than the section 5 rule, and each rule wins.

### 12.4 Why 2733 tests passed while the header looked wrong

Rule 4 of `contracts/ui-testids.md` states that a test selects by `data-testid`
alone. No test in this repository read a painted color. The unit test
`test_a_theme_sets_every_property_the_base_stylesheet_reads` proves that a theme
sets every property. It cannot prove that the property reaches the paint.

`tests/e2e/upgrade_portal/test_assets.py` now holds
`TestThemeColorsReachThePaint`. It reads `getComputedStyle` for five elements
under both shipped themes, and it reads the text decoration of a link button.

A revert of the two fixes gives this:

| Case | Cases | Result against the reverted stylesheet |
| --- | --- | --- |
| Brand text and resting navigation link | 4 | fail |
| Link button color | 2 | fail |
| Link button text decoration | 2 | fail |
| Active navigation tab | 2 | pass |

The two active tab cases pass because that rule never lost. They guard the token
and not the specificity, and this table records that difference.

### 12.5 A suspected third defect, disproved

The browser console reported a policy violation after a page probe:

```
Applying inline style violates the Content Security Policy directive: "style-src 'self'"
```

`portal.js:648` sets `bar.style.width` for the progress bar, so that line looked
like the cause. A direct test of the policy refuted the reading:

| Call | Result |
| --- | --- |
| `element.style.width = '42%'` | allowed, and the value reads back |
| `element.setAttribute('style', 'width: 43%')` | blocked, and the value stays `42%` |

The policy blocks the `style` attribute of the markup. It does not block the
`style` property of an element, and the comment at `portal.js:645` already said
so. A second console read across all nine pages, with no probe of my own in
flight, reported no violation on any page.

The instrument created the symptom. `portal.js:648` is correct. No defect is
recorded here.

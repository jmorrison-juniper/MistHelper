disk that the task was delivered and verified. A task box is not proof. A task
that names an identifier is proven only when that identifier runs.

carries no proof. The second half scrubs the tasks that keep their check and
reports the defects inside them.

### 2.1 Warning: the portal can report a stopped device while that device writes firmware

An operator who reads the word stopped can cut power to a switch. A switch that
loses power while it writes firmware does not start again. Both defects below
produce that reading.

#### Defect 1. A MAC address with dash separators never matches the guard. Verified

```
src/firmware/upgrade_service.py:801  frozenset(str(value).replace(":", "").replace("-", "").lower() ...)
src/firmware/upgrade_service.py:842  already = tuple(mac for mac in macs if mac.replace(":", "").lower() in writing)
src/firmware/upgrade_service.py:843  stopped = tuple(mac for mac in macs if mac.replace(":", "").lower() not in writing)
```

Line 801 removes the colon and the dash. Lines 842 and 843 remove the colon
alone. A MAC address written `aa-bb-cc-dd-ee-ff` therefore never matches a set
member. The device always falls into `stopped`.

The message at `:820` then states that no device was writing firmware.

**Fix**: give the three lines one shared normalizing function.

#### Defect 2. Every session smart router reports as stopped. Verified

The chain runs through five files and each step is correct on its own.

| Step | Line | What happens |
| --- | --- | --- |
| 1 | `upgrade/options.py:416-418` | A session smart router always uses the organization scope |
| 2 | `firmware/upgrade_service.py:910-911` | At that scope the status read calls `listOrgDevicesStats`, which returns device statistics and not an upgrade job |
| 3 | `firmware/upgrade_service.py:936` | The list becomes the mapping `{"devices": [...]}` |
| 4 | `firmware/upgrade_service.py:793-801` | That mapping holds neither `reboot_in_progress` nor `targets`, so the reader returns an empty set |
| 5 | `firmware/upgrade_service.py:841-843` | An empty set puts every MAC address into `stopped` |

The operator then reads that the cloud stopped every device and that no device
was writing firmware. The code cannot know either fact at the organization
scope.

Step 1 and step 2 are both deliberate. `data-model.md:281-289` fixes the scope,
and the seam must never call `getOrgSsrUpgrade`, because the installed SDK
builds the cancel path inside that function. The defect is that the reader
treats an unknown state as a known safe state.

**Fix**: make the reader answer "unknown" instead of an empty set when the
payload holds no upgrade job. Report the devices as unknown, never as stopped.
`upgrade/stop.py:204` must not set `status_known` to true for that answer.

### 2.2 High

#### Defect 3. The takeover that needs the typed word CONFIRM cannot run in production. Verified

```
src/upgrade_portal/runtime/lock.py:114  LOCK_TTL_SECONDS: Final[int] = 300
src/upgrade_portal/runtime/lock.py:119  COOLDOWN_SECONDS: Final[int] = 300
```

The lease and the cooldown are the same length. A refresh writes the timestamp
and the 300-second expiry together, at `:1076-1080`. The test for a quiet holder
is an age of 300 seconds or more, at `:636`.

The key therefore dies at the same moment that its holder turns quiet. A second
operator finds no key. The plain acquire at `:903` succeeds and returns
`ACQUIRED` at `:1028`.

The whole takeover branch at `:986-999` needs a key that still lives and that
already turned quiet. No such moment exists. The typed word `CONFIRM`, the
takeover audit record, and the audit line are all unreachable. The same defect
disables the resume guard at `:958-964`, which asks for the typed word
`continue`.

This defeats two of the five closed decisions about identity and locking.

**Fix**: make the cooldown strictly shorter than the lease. A cooldown of 300
seconds needs a lease of more than 300 seconds. The heartbeat runs every 60
seconds at `:124`, so a lease of 420 seconds keeps seven heartbeats of margin
and leaves a 120-second window in which the takeover can run.

**Fixed** in `3d83930`, "make the lock lease outlive the cooldown so a takeover
can run". The two code lines above are the state before that commit. The shipped
value is `LOCK_TTL_SECONDS: Final[int] = 3600` at
`src/upgrade_portal/runtime/lock.py:117`, and `COOLDOWN_SECONDS` stays at 300.
The lease is therefore 3600 seconds and not the 420 seconds this paragraph
proposed, so the takeover window is 55 minutes and not 2 minutes. A longer
window is safer here. The second operator reaches the typed word `CONFIRM` for
the whole hour after the first operator turns quiet, instead of losing the site
to a plain acquire 2 minutes later.

The same commit repaired the test double that hid the defect. `ScriptedLockStore`
returned a value with no expiry test, recorded an expiry it never acted on, and
seeded a lock with no lease. Every takeover test therefore seeded a state that no
real server can produce.

#### Defect 4. An open endpoint drives two store writes for each call. Verified

`GET /readyz` at `src/upgrade_portal/app/factory.py:467` carries no session
guard. The portal registers no request throttle of any kind. The only global
hook is the optional address allow list at `app/security.py:152`, and that hook
registers nothing when the list is empty, which is the shipped default. The
cross-site request forgery check covers a state-changing request alone, so a
`GET` passes it.

Each call then performs real work:

```
factory.py:346-353  create the collection when absent, insert a document, read it back
factory.py:371-373  write a key into the lock store, read it back
```

Any client that reaches the port drives one document store write and one lock
store write for each request. The writes use one fixed key each, so the stored
data never grows. The load on both stores does grow.

**Fix**: bind the readiness answer to a short cache, or move the write probe
behind the address allow list. Do not remove the write probe. It exists because
a read-only replica answers a ping and refuses every write, and the site lock
would then fail for every operator while the probe reported the store ready.

**Fixed** by the short cache. Section 14 records the window, the reason for its
length, and the evidence. The write probe stays.

### 2.4 The settle gates can wait with no visible cause

The settle logic is the part of this feature that decides when the second
capture is safe. Four faults made it wait longer than it should, or forever,
with nothing in the page to explain the wait. All four are now closed. Read the
paragraphs after the table, because one of the four was not the fault the first
reading named, and the work found a fifth gap that stays open.

| Defect | Line | What happens | State |
| --- | --- | --- | --- |
| 7. A truncated event page drops the reconnect message | `upgrade/events.py:446-448` computes and warns about `truncated`. `drain_device_events` at `:483-491` never reads it | The gate misses the one message it waits for and waits forever | Fixed |
| 8. The event read carries no guard | `upgrade/events.py:416` calls the cloud with no `try`. The definition read at `:229` has one | One cloud fault ends the watch | Fixed |
| 9. A failed statistics read looks like an empty answer | `upgrade/gate.py:846` catches every fault and returns an empty reading | The device waits and the page names no cause | Fixed. The first reading was wrong. See below |
| 10. Three settle signals collapse to two | `upgrade/gate.py:666-668` accepts a version change alone when the earlier uptime is null | The gate can pass a device that never rebooted, against T141 | Fixed |

**Defect 7**: `drain_device_events` now reads the `truncated` flag. A full page
with no cursor hides the rest of that window, so the reader halves the window and
reads both halves. Three splits turn one window into at most eight parts and cost
at most 15 calls, which one 20-second round affords. The page ceiling keeps its
warning and never splits, because ten full pages plus splits would break the call
budget. A split that reaches either floor stops and warns. No path turns a
truncated read into a failed run.

**Defect 9 was not the fault the first reading named.** The guard at
`upgrade/gate.py:846` exists, it logs, and it builds a `partial_reasons` entry.
The fault was that the reason reached the log and stopped there.

This is one fault variety, and this section holds three of it: a mechanism with a
producer, a docstring, and no consumer. Defect 7 is the first, where
`EventPage.truncated` had a writer and no reader. Defect 9 is the second, where
the reason reached a log alone. The open gap at the end of this section is the
third, where `PhaseProgress` has a type and no live channel. No gate finds this
variety. A field with no reader breaks no test, because the test that would fail
is the one nobody wrote.

The fix carries the cause to the page. `_read_statistics` turns the machine
reason into one operator sentence, `_round` joins it with the event cause,
`_wait` keeps the cause of the last round, `_timeout` puts it on the
`PhaseOutcome`, `_write_phase` writes it into the run record, `_phase_entry`
carries it into the status body, and the page paints it every 30 seconds. A
phase that settled carries no note, because a phase that settled needs no cause.

**A projection nearly dropped the fix.** `runtime/runs.py _phase_entry` wrote
exactly five keys and discarded every other key of the stored record. Without
that edit the note would have reached ArangoDB and never reached the browser. The
general rule, now proven twice: when adding a field to a stored record that must
reach a page, read the projection between the store and the view. A field written
is not a field delivered.

**Defect 10**: the branch order was the fault. The test for a missing earlier
uptime sat first and returned true with no further test, so `_anchor_proves_reboot`
could run only when the earlier uptime was present, which is the one case it was
never written for. The branches now run strongest first. Two real uptime readings
decide the answer alone. Only a missing reading reaches the absolute anchor, and
only a missing anchor reaches the version-only path.

**Newly found, and open: no phase progress reaches the page during a wait.**
The run record holds one write site for `phases`, at `upgrade/driver.py:1299`,
and it runs only after `settle()` returns. `app/wiring.py:630` calls
`lock_heartbeat` with two arguments, so the progress sink of the plan is null in
production. The phase entry therefore holds its opening values until the phase
ends, then jumps. `upgrade/phase_gate.py:84-92` states the opposite in its own
docstring: "the operator sees the count rise during the wait instead of seeing
one answer at the end". That sentence is false. This is a false docstring, which
is worse than an unused field, because a later reader trusts it.

This gap is a design change, not a defect fix. A live channel means one store
write for each round, which is 30 to 90 extra writes for each phase. It stays out
of this fix on purpose.

Defect 17 needed a correction of its own record. The first citation named two
line numbers that no longer resolve, and it described the harm as a swap of the
pointer on the run record. A read of the code proved something different.
`build_capture_id` names the capture from the run alone and hardcodes the first
ordinal, so every manual pre-check of one run carries the same identifier. The
capture collection keys on that identifier, so the second reading replaces the
first stored document in place. The pointer never changes, because the two
readings share one name.

A fresh ordinal looked like the smaller fix. It is wrong. `capture/assembly.py`
derives the `role` field of the assembled record from the ordinal, so a repeat
pre-check given the third ordinal would assemble a document that calls itself a
post-check. The route refuses instead. It answers `409 pre_check_locked` when the
named run passed firmware submission, which is earlier and safer than the point
the brief names. Before submission the replacement is what the operator asked
for, so the route accepts it.

Defect 16 needed a correction of its own record. The brief placed the guard
inside `build_options`. A read of the callers proved that wrong. That function
serves two paths that mean different things. `options.py:746
build_options_record` runs when the operator chooses a moment in the browser.
`app/wiring.py:437 build_plans` replays a choice that the operator already made
and that the save call already bounded. `build_plans` catches every fault and
returns an empty plan at `:441`, which fails the whole run. A guard on the
shared function would therefore turn a run that waits for confirmation past its
own start time into a failed run. That is the reading the lost lock work already
refused, because a failure that is not a failure teaches an operator to distrust
the report.

The guard sits on the choosing path alone. `build_options` takes the clock as an
argument and defaults it to the real clock, so a new choosing path inherits the
guard without asking for it. The replay path opts out with `now=None` and says
why on the line above. A new replay path that forgets raises a refusal that a
test catches, which is the safer of the two ways to be wrong.

The window has two edges. `options.py:72 START_TIME_GRACE_SECONDS` allows 120
seconds of drift, because the clock of the browser and the clock of the portal
rarely agree to the second. `options.py:78 START_TIME_HORIZON_SECONDS` allows one
year, because a millisecond epoch pasted into the field names a moment tens of
thousands of years ahead. The cloud accepts that value and the upgrade never
runs, so the operator waits for work that can never start.

The test that the guard broke is the defect in miniature.
`test_a_start_time_of_digits_becomes_epoch_seconds` asserted on the epoch
`1770000000`, which names a moment in February 2026. That moment aged into the
past while the file sat on disk, in the same way that a saved start time ages.
The replacement injects a fixed clock, so it can never age again.

Defect 18 needed a correction of its own record. The brief named two page walks
and cited `app/routes/select.py:303`. That line number was stale, because the
truncation sat at `:314`. A sweep for the whole class then found a third page
walk at `upgrade/options.py:156 _read_paged`. That third walk holds no defect.
It names a reason on a fault and it counts a short read, so it is the model that
the other two now follow.

Both repairs add a parameter, and both parameters are required. A default would
be fail open, because a new caller that forgets the argument would drop the
identifier from the log record and leave the same silence behind. A required
parameter stops a new caller at the gates instead. `_paged` takes the whole
`SiteScope`, not the site identifier alone, because all four callers already
hold that value and the module already passes it by that name.

The `pagination is None` branch of `collect_pages` writes no log record. That
branch discards nothing. It returns the only page that the software development
kit can give, and one page is a correct answer for a small organization.

One line of the fault-message class closed here. The old `_paged` logged the
message of a caught fault, which a driver may fill with a connection string. It
now logs the class name alone. A sweep of the package found 14 more sites of

The true defect sits one step earlier. A refused call reaches `guard_page_count`

## 8. Addendum. Defect 24, the portal that forgot every run at once

### 8.1 Warning: every write claimed success and every read denied the run. Verified

`capture/store.connect_database()` answers None when no ArangoDB server answers.
`DocumentRunStore.write_run` still reported success in that state, because it

### 8.2 The fix

`app/wiring.py:87-89` holds a bounded process-local mirror behind one lock.

| Line | What it holds |
| --- | --- |
| `wiring.py:87` | `_MIRROR`, the runs of this process, oldest first |
| `wiring.py:88` | `_MIRROR_GUARD`, because the driver thread writes while the poll reads |

| `wiring.py:112` | `mirrored_run`, the fallback of the single read |
| `wiring.py:126` | `mirrored_site_runs`, the fallback of the site list |

## 11. Addendum. Defect 28, the capture that verifies and cannot be read

A third by-eye drive found this one. It is a defect of the browser harness and
not of the shipped portal, and the section states that plainly. The harm is real
anyway, because the harness told every reader that a broken endpoint worked.

### 11.1 Warning: the read endpoint answered 500 for a verified capture. Verified

An operator opened `/captures/new?site_id=e2e-site-0001`, chose tier 2, and
pressed the start control. The capture ran to the end. The result panel showed
the verified badge, and the browser console showed this:

```
Failed to load resource: the server responded with a status of 500
The stored size read failed. server_error 500
```

The stored size then read `0` for the rest of the session.

The timing invited a race reading, because the first 500 arrived 45 milliseconds
after the start and the store write landed 688 milliseconds later. A second read,
taken from inside the page after the capture reached the verified state, refuted
that reading:

| Endpoint | Status | Body |
| --- | --- | --- |

### 11.2 The cause. One settings key, two readers, two shapes

Two route modules read the one Flask settings key `CAPTURE_LOADER`:

| Module | Constant | Line |
| --- | --- | --- |
| `app/routes/capture.py` | `LOADER_KEY` | 69 |
| `app/routes/review.py` | `CAPTURE_LOADER_KEY` | 196 |

They accept different shapes. `review.py:438` accepts the record of the store
**and** a bare document, and its docstring states that it does so to keep a test
stand-in small. `capture.py:895` accepts the record alone, because it reads
`comparable` to decide whether the document may leave the portal.

The browser stand-in answered a bare document. `capture.py` therefore refused
every read, `refusal_for` read an empty reason, and an empty reason is not a key
of `REFUSAL_STATUS`, which holds `capture_not_found` and `capture_not_verified`
alone. The route fell through to the 500.

The shipped portal is not affected. `capture.py` resolves `store.load_capture`
and `review.py` resolves `store.load_capture_for_comparison`, and both return a
`CaptureLoad` record. The fault lives in the stand-in of
`tests/e2e/upgrade_portal/conftest.py`, whose own docstring claimed a shape that
`read_capture` accepts. That claim was false.

The quick fix is to make `capture.py` accept a bare document, the way `review.py`
does. That fix is dangerous. A bare document carries no `comparable` flag, so the
route would hand out a half-written capture. `store.load_capture_for_comparison`
exists to stop exactly that, and its docstring says so.

The stand-in is the wrong part, so the stand-in is the part that changed.
`conftest.py` now answers a frozen `StandInCaptureLoad` record with the three
names `capture`, `comparable`, and `reason`. One assignment still serves both
route modules, because both read the same key string.

Do not "fix" the other empty-reason path. `store.py:68` names
`database_unreachable`, that reason is also absent from `REFUSAL_STATUS`, and it
also produces a 500. That is deliberate and is held by
`tests/contract/upgrade_portal/test_capture_read.py:432`, whose reason states
that a 404 would tell an operator that the capture is gone, and the operator

## 14. Addendum. Defect 4, fixed by a short cache

Section 2.2 records that `GET /readyz` drives one document store write and one
lock store write for each call, and that the endpoint carries no guard. This
section records the fix.

### 14.1 The approach, and the two the fix refused

Section 2.2 offers two fixes. The shipped fix is the first one, a short cache.

The fix does not move the probe behind the address allow list. That list is
empty in the shipped default, so the hook registers nothing. An operator who
never sets the list would lose the readiness endpoint, and an orchestrator
cannot sign in to reach it.

The fix does not remove the write probe. Section 2.2 states the reason. A
read-only replica answers a ping and refuses every write. The probe would then
report the store ready while the site lock failed for every operator.

### 14.2 The window is 5 seconds

The load-bearing property is that the window is shorter than the interval an
orchestrator uses. A genuine probe then always finds the entry expired and
always does real work. Only the extra calls inside the window read the cache.

Two readings in this repository set the length:

```
Containerfile:117   HEALTHCHECK removed for OCI and Podman compatibility
Dockerfile:109      the same note
compose.yml:88-93   arangodb, interval 10s
compose.yml:109-114 redis-stack, interval 10s
```

The portal container ships no health check of its own, so no in-repo interval
binds the portal directly. The two store containers probe every 10 seconds. A
5-second window therefore sits below the shortest interval this repository
states, and it stays below the 10-second cadence an orchestrator conventionally
uses.

The cost is a detection delay of 5 seconds at most. That is half of the
neighboring probe interval, and it is small against the 5 retries both store
health checks allow.

### 14.3 The lock removes a thundering herd as well

Waitress runs 4 threads. Gunicorn runs several worker processes. A cache for
each process is correct, because each worker must answer on its own.

One `threading.Lock` guards the read and the refresh together. While one thread
probes, the other threads wait and then read the value it wrote. Four worker
threads therefore drive one probe pair and not four. The worst-case latency does
not change. The load on both stores falls to a quarter.

The code stamps the entry after the probe returns, never before. A thread that
waited behind a slow probe would otherwise read a stamp older than its own wait
and probe again, which is the herd the lock removes. A comment above the
assignment records this.

### 14.4 Why the cache holds a dictionary and not two module names

`pylint` runs on `src/` alone, at `.github/workflows/ci.yml:328`, and
`global-statement` is W0603, which is on by default. A function that rebinds a
module name needs the `global` statement. A function that mutates a container
needs nothing. The cache is therefore a module-level dictionary that the code
only ever mutates.

### 14.5 The evidence. Two reverts

A test that passes for the wrong reason is worse than no test. Each revert broke
the fix one way, and the run recorded which tests noticed.

| Revert | Result |
| --- | --- |
| A. The window is 0, so every call probes | 1 failed, 19 passed |
| B. A new application inherits the earlier answer | 12 failed, 8 passed |

Revert A earns the new test. One test fails, and it is the burst test. The other
19 tests pass with the cache disabled, which proves the cache changed no
documented behavior of the endpoint.

Revert B earns one line. `register_readiness` drops the cached answer for each
new application. Remove that line and 12 tests fail. Nine of them are older than
this fix. Every fixture in `tests/contract/upgrade_portal/conftest.py` is
function-scoped, so each test builds a new application. Without the reset, a
stale answer leaks from one test to the next. That one line is why 13 of the 14
older test functions needed no edit at all.

One older test did need an edit. `test_repeat_probes_write_a_fresh_value` calls
the endpoint twice against one application. Its subject is the probe and not the
cache, so it now drops the cached answer between the two calls. The assertion
did not change.

| Suite | Before | After |
| --- | --- | --- |
| `tests/unit` and `tests/contract` for the portal | 2599 passed | 2602 passed |

The three new cases are the burst, the reset, and the new application. No older

## 15. Addendum. Defect 33, the fault message that three readers see

Defect 20 closed one line of a class of faults. This section closes the class.
The class has 14 small cases in log lines. It has one large case that reaches
the browser.

### 15.1 Warning: a connection string could reach the run record. Verified

The run state machine states the rule for its own field. `runtime/runs.py:431`
reads:

```text
message: One plain sentence for the operator. Never a credential.
```

The driver broke that rule. `upgrade/driver.py` wraps the whole upgrade journey
in one catch block:

```python
try:
    self._submit(record)
    self._cascade(record)
except Exception as error:  # noqa: BLE001  # WHY: The thread must write the reason, never die silently.
    self._fail(record, error)
```

The old `_fail` wrote `str(error)` into `record["error"]["message"]`. That block
covers every ArangoDB write, every Redis call, and every cloud call of the run.
A Redis connection fault names its own client:

```text
Error 111 connecting to redis://:<the password>@10.0.0.9:6379. Connection refused.
```

Four readers hold that field. ArangoDB stores it. The CSV backup writes it. The
browser paints it on the run page. The log line beside it repeats it. A password
belongs in none of the four.

### 15.2 The trust test, and the two designs this audit refused

The repair needs a trust test. Some faults carry a sentence that the portal wrote
for the operator, and that sentence must pass through whole. Every other fault
must lose its text.

The first design tested one class:

```python
if isinstance(error, RunDriverError):
```

That guard is itself a defect, and a count of the package proves it. This search

```text
^class \w*(Error|Exception)\(
```

reports 17 fault classes in 9 modules of `src/upgrade_portal`. Only one of them
is `RunDriverError`, at `upgrade/driver.py:214`. The settle gate defines a class
of its own at `upgrade/phase_gate.py:80`:

```python
class PhaseGateError(RuntimeError):
```

`PhaseGateError` is not a subclass of `RunDriverError`. The gate raises it at
`upgrade/phase_gate.py:456` with a sentence that the portal wrote:

```python
raise PhaseGateError(f"One phase polls one device family, and this phase holds {sorted(families)}.")
```

The first design would drop that sentence. It would drop the sentence of 16
classes.

The second design added a marker class that every fault class inherits. That
design needs an edit in 17 classes across 9 files. Three of those classes extend
`ValueError`, and existing catch blocks depend on that. Each of the three would
then need multiple inheritance. The cost is too high for a repair of one field.

### 15.3 Why the module name is the right proof

The property that the repair needs is authorship. The question is not which class
the fault holds. The question is who wrote the message. A module name answers
that question directly:

```python
def portal_wrote(error: BaseException) -> bool:
    return type(error).__module__.startswith(PORTAL_PACKAGE)
```

`PORTAL_PACKAGE` is the text `src.upgrade_portal.`. The final period stops a
match on a future package named `src.upgrade_portal_extra`.

The design holds only while no module of the package builds a fault message from
the text of a caught fault. One search is weak evidence, so this audit ran three
searches of different shapes.

| Search | Shape | Result |
| --- | --- | --- |
| `raise \w*(Error\|Exception)\([^)]*\b(error\|fault\|exc)\b` | One line | No match |
| the same search with `multiline` | Across lines | No match |
| `\{(error\|fault\|exc\|err)[.!:}]\|str\((error\|fault\|exc\|err)\)` | Any read of a fault | 4 sites |

The third search is the strongest, because it does not depend on the word
`raise`. It found four sites, and all four are safe:

| Site | Why it is safe |
| --- | --- |
| `app/routes/auth.py:821` | The text dies inside a truth test |
| `app/routes/select.py:1413` | The parameter is `lock.SiteLockError`, a class of this package |
| `upgrade/driver.py:1046` | The guarded read inside `operator_reason` |
| `upgrade/driver.py:1065` | The guarded read inside `failed_stage` |

The upgrade seam sits outside the package, and it stays outside on purpose.
`src/firmware/upgrade_service.py` raises a bare `ValueError` at seven lines, and
each message is plain. The module of `ValueError` is `builtins`, so the portal
sanitizes all seven. That is the right call. `requests` and `mistapi` raise
`ValueError` too, and a class of the standard library proves no authorship.

The check also fails in the safe direction. A rename of the package would
sanitize more messages, never fewer.

### 15.4 The diagnostic this repair gives up

The foreign message is now gone from the record and from the log. The reader
sees the class name alone:

```text
The run stopped after the fault ConnectionError.
```

That name says which library failed. It does not say which host or which port.
This audit accepted the loss, because two other options failed a check.

A second field on the record would carry the text to ArangoDB, to the CSV
backup, and to the browser. That is the same defect under a new name.

A log line at debug level would keep the text for an engineer. Debug records
travel to a log collector, so that option moves the credential and does not
remove it.

For the same reason, the sentence of a foreign fault does not tell the operator
to read the log. The log holds the class name alone.

### 15.5 The stage the operator reads

`_fail` writes a stage beside the message. The old code read the message of any
fault to pick that stage. The new code reads the message of a portal fault only:

```python
def failed_stage(error: BaseException) -> str:
    if portal_wrote(error) and POST_CHECK_MARK in str(error):
        return STAGE_POST_CAPTURE
    return STAGE_UPGRADE
```

One portal sentence holds the text `post-check`. The driver raises it when the
post-check capture fails to start. A foreign fault now always reads as the
upgrade stage, which is the safe direction. The upgrade stage covers the larger
part of the journey, so it sends the operator to the wider search.

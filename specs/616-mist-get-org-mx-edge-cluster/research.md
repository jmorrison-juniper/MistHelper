# Phase 0 Research: getOrgMxEdgeCluster

**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)
**Endpoint**: `GET /api/v1/orgs/{org_id}/mxclusters/{mxcluster_id}`
**Source doc**: `documentation/api/orgs/GET_orgs_org_id_mxclusters_mxcluster_id.md`

This document records the Phase 0 unknowns enumerated by the plan template
and the decisions taken to unblock Phase 1 design.

---

## Research Task 1: SDK function signature & behavior

### Decision

The MistHelper menu method will call:

```python
mistapi.api.v1.orgs.mxclusters.getOrgMxEdgeCluster(
    apisession,                # The shared mistapi.APISession instance
    org_id=org_id,             # UUID string from .env or user prompt
    mxcluster_id=mxcluster_id, # UUID string from user prompt
)
```

The call returns a `mistapi.APIResponse` whose `.data` attribute is a single
JSON object (an `MxCluster` per the OpenAPI schema), not an array. The
function is non-paginated.

### Rationale

The enriched per-endpoint doc
(`documentation/api/orgs/GET_orgs_org_id_mxclusters_mxcluster_id.md`) lists
the SDK target as `mistapi.api.v1.orgs.mxclusters.getOrgMxEdgeCluster()` and
identifies two required path parameters (`org_id`, `mxcluster_id`) with no
query parameters and no request body. The 200 response schema is a single
object (`description: MxCluster`), not an array, so pagination logic does
not apply. The response includes nested configuration objects (`mist_das`,
`mist_nac`, `mxedge_mgmt`, `proxy`, `radsec`, `radsec_tls`,
`tunterm_dhcpd_config`, `tunterm_extra_routes`) plus several arrays
(`tunterm_ap_subnets`, `tunterm_hosts`, `tunterm_hosts_order`,
`tunterm_monitoring`).

### Alternatives considered

- **Calling `listOrgMxEdgeClusters` first and filtering by id**: rejected.
  Wastes an API call and forfeits the ability to load a single cluster when
  the list call would be heavy.
- **Passing IDs positionally**: rejected. The mistapi SDK accepts both
  positional and keyword arguments; keyword form is used throughout
  MistHelper for readability and to survive future SDK signature
  reordering.

## Research Task 2: Primary Key Strategy

### Decision

Register `getOrgMxEdgeCluster` in `ENDPOINT_PRIMARY_KEY_STRATEGIES` with
strategy type `natural_pk`, primary key `["id"]`, and indexes
`["org_id", "site_id", "name"]`.

```python
"getOrgMxEdgeCluster": {
    "type": "natural_pk",
    "primary_key": ["id"],
    "indexes": ["org_id", "site_id", "name"],
    "unique_constraints": [],
    "description": "Single Org MxEdge cluster configuration record",
},
```

### Rationale

The response object exposes a stable UUID `id` field (the cluster's UUID
in the Mist organization) marked `readOnly` in the OpenAPI schema. The
same UUID is what the user supplies as the `mxcluster_id` path parameter,
so it is guaranteed unique within an org and stable across runs. This
matches the existing `listOrgMxEdgeClusters` strategy (already registered
at line ~3971 of `MistHelper.py` with `type: natural_pk`, `primary_key:
["id"]`) so single-item fetches upsert into the same logical row that a
list fetch would write. Indexing `org_id`, `site_id`, and `name` supports
common UI / report joins (find all clusters in an org, find a cluster by
human name, find the cluster bound to a site).

### Alternatives considered

- **`auto_increment_with_unique`**: rejected. The natural `id` is stable
  and unique; auto-increment would defeat upsert semantics and silently
  accumulate duplicates on re-fetch.
- **`composite_pk` on `(org_id, id)`**: rejected. `id` is already unique
  across orgs by Mist API contract; the composite adds no protection.
- **Different table from `listOrgMxEdgeClusters`**: rejected. Single-fetch
  and list-fetch return rows of the same logical entity. Using a shared
  table would require schema reconciliation; the simpler decision (taken
  below in Task 3) is to use a *different* table name (`org_mx_edge_cluster`
  vs the plural-named table from the list endpoint) because the list
  endpoint returns trimmed records while the single-fetch returns the full
  configuration including secrets-bearing nested objects, and we do not
  want the slimmer list rows to silently overwrite the richer single rows.

## Research Task 3: Output filename and SQLite table

### Decision

- CSV filename: **`OrgMxEdgeCluster.csv`** (one file per run, overwritten on
  each invocation per existing MistHelper convention).
- SQLite table name: **`org_mx_edge_cluster`** (singular -- it stores
  single-item fetches; one row per `(org_id, mxcluster_id)` query).
- ArangoDB collection name: **`org_mx_edge_cluster`** (matches the SQLite
  table to keep cross-backend grep simple).

### Rationale

MistHelper convention for org-scope exports is `Org<EntityName>.csv` with
PascalCase. The closest existing neighbor is the plural `OrgMxEdges.csv`
generated by `OrgExportUtils.mx_edges()`. Using `OrgMxEdgeCluster.csv`
(singular) communicates that the file holds the configuration of a single
cluster fetched by id, rather than a list. The SQLite table is named
`org_mx_edge_cluster` (snake_case singular) to match. Using a name distinct
from any table backing `listOrgMxEdgeClusters` avoids accidental schema
collisions when both list and single-item exports are run in the same
session.

### Alternatives considered

- **`OrgMxClusters.csv` / `org_mxclusters`**: rejected. Matches the API path
  segment but is plural, which is misleading because each row is a single
  fetch by id.
- **Sharing the table with the list endpoint**: rejected -- see Task 2
  alternatives.
- **`MxCluster_<id>.csv`** (filename per cluster): rejected. Breaks the
  established one-file-per-menu-item convention and makes batch testing
  harder.

## Research Task 4: Menu category placement and next available menu number

### Decision

Proposed menu number: **96**, placed in the Interactive Safe Org Exports
cluster (operations 60-96), alphabetically near the existing MxEdge
exports.

### Rationale

The MistHelper menu ranges documented in `.github/copilot-instructions.md`
are:

- 1-59: Safe Org Exports
- 60-96: Interactive Safe
- 97-101 + 153: Resource Intensive
- 102-123: WebSocket
- 124-150: Interactive
- 151-152: Continuous
- 154-194: Destructive

This endpoint is read-only, requires interactive prompts for `org_id` and
`mxcluster_id`, and returns a small payload. That places it firmly in the
Interactive Safe Org Exports band (60-96). Slot 96 is the upper boundary
of that band and is currently unallocated in this worktree's tree. The
adjacent existing operations for org MxEdges (e.g.
`OrgExportUtils.mx_edges` -> `listOrgMxEdges`) sit in the same band, so
placement is contextually consistent.

### Alternatives considered

- **Slot 1-59 (Safe Org Exports)**: rejected. Those operations are
  prompt-free; this endpoint requires the user to supply a specific
  `mxcluster_id`, which is interactive.
- **Slot 97-101 (Resource Intensive)**: rejected. Single GET on a small
  config object is not resource intensive.
- **Slot 124-150 (Interactive)**: rejected. That cluster is reserved for
  diagnostics / management / packet captures, not org exports.

The final menu number is re-verified at `/speckit.tasks` time against
other in-flight feature branches; if 96 collides, the next free integer in
the same band is used.

## Research Task 5: Required user prompts

### Decision

The menu method collects:

1. **`org_id`** -- prompt only if the environment variable `MIST_ORG_ID` is
   unset; otherwise default to the env value. Prompt text:
   `"Org ID (default from MIST_ORG_ID): "`. Context:
   `"org_mx_edge_cluster:org_id"`.
2. **`mxcluster_id`** -- always prompt; no env override. Prompt text:
   `"MxEdge Cluster ID: "`. Context:
   `"org_mx_edge_cluster:mxcluster_id"`.

Both values are validated against the Mist UUID shape
(`re.fullmatch(r"[0-9a-fA-F-]{36}", value)`) before the API call. On
validation failure the method logs a `WARNING` and returns early without
calling the SDK.

### Rationale

- `org_id` is the single most-used identifier in MistHelper. The existing
  convention (visible across `OrgExportUtils` methods) is to pull it from
  `.env` by default and let the user override interactively when working
  multi-tenant. This keeps automated test runs (`python MistHelper.py
  --test`) non-interactive.
- `mxcluster_id` is per-invocation and has no sensible default in `.env`.
  Forcing a prompt every time prevents a stale env value from silently
  steering the wrong cluster.
- `safe_input()` is used for both prompts so EOF in SSH / container
  contexts exits cleanly with code 0.

### Alternatives considered

- **Letting `mxcluster_id` default to `MIST_MXCLUSTER_ID` env var**:
  rejected. The cluster identifier changes per investigation; an env
  default would invite accidental fetches against the wrong cluster.
- **Auto-discovery via `listOrgMxEdgeClusters`**: deferred. A "pick from
  list" UX is appealing but exceeds the scope of this single-endpoint
  menu item and would add a dependency on the list endpoint's local
  state. Tracked as a follow-up improvement only if the user requests it.
- **Skipping UUID validation**: rejected. Sending a malformed id to the
  Mist API wastes a round trip and produces a less actionable error than
  a local `WARNING`.

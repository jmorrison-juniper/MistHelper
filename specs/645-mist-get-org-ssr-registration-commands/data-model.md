# Phase 1 Data Model: getOrgSsrRegistrationCommands

**Feature**: `645-mist-get-org-ssr-registration-commands`
**Endpoint contract**: [contracts/get_org_ssr_registration_commands.md](./contracts/get_org_ssr_registration_commands.md)

## Entities

The endpoint returns exactly one JSON object per invocation. It is not an entity in the
Mist data model -- it is a *rendered registration command* generated on demand. MistHelper
persists each invocation as one row for audit purposes.

### Entity 1: `OrgSsrRegistrationCommand`

Represents a single fetch of the SSR onboarding commands for a given org. Fields marked
"client-side" are added by MistHelper at persist time and are not part of the API
response.

| Field                     | Type                | Nullable | Source        | Notes                                                                                       |
|---------------------------|---------------------|----------|---------------|---------------------------------------------------------------------------------------------|
| `misthelper_internal_id`  | INTEGER             | No       | client-side   | Auto-increment surrogate primary key.                                                       |
| `org_id`                  | TEXT (UUID)         | No       | client-side   | Org this fetch was scoped to. Foreign key to `orgs.id` if the orgs table is present.        |
| `ttl_requested_seconds`   | INTEGER             | Yes      | client-side   | The `ttl` query parameter value the operator supplied, or NULL when SDK default was used.   |
| `asset_ids_requested`     | TEXT (JSON array)   | Yes      | client-side   | JSON-encoded list of asset UUIDs, or NULL when the fetch was not asset-restricted.          |
| `conductor_cmd`           | TEXT                | Yes      | API response  | Command to run on the Mist Conductor to accept the registration.                            |
| `registration_code`       | TEXT                | Yes      | API response  | Short-lived registration code embedded in the SSR shell command. Treat as a secret.         |
| `router_shell_cmd`        | TEXT                | Yes      | API response  | Full shell command the operator runs on the SSR to complete adoption.                       |
| `fetched_at`              | TIMESTAMP (UTC ISO) | No       | client-side   | UTC timestamp of the successful API call.                                                   |

**Primary key**: `misthelper_internal_id`
**Unique constraint**: `(org_id, registration_code, fetched_at)` -- prevents accidental
duplicate rows if the same fetch is imported twice, while still allowing repeated fetches
that legitimately produce different `registration_code` values.
**Foreign keys**: `org_id` logically references the `orgs.id` column when the `orgs`
table is present in the same SQLite file; the constraint is not enforced at the DDL level
because MistHelper populates tables lazily.

### State Transitions

**N/A -- read-only endpoint.** Every row is immutable once inserted. There is no update
path; a refresh yields a new row with a new `misthelper_internal_id` and a new
`fetched_at`. The `registration_code` naturally expires on the Mist side after `ttl`
seconds, but MistHelper does not track that server-side expiration.

## SQLite DDL

```sql
CREATE TABLE IF NOT EXISTS org_ssr_registration_commands (
    misthelper_internal_id INTEGER PRIMARY KEY AUTOINCREMENT,
    org_id                 TEXT    NOT NULL,
    ttl_requested_seconds  INTEGER,
    asset_ids_requested    TEXT,
    conductor_cmd          TEXT,
    registration_code      TEXT,
    router_shell_cmd       TEXT,
    fetched_at             TEXT    NOT NULL,
    UNIQUE (org_id, registration_code, fetched_at)
);

CREATE INDEX IF NOT EXISTS idx_org_ssr_reg_cmd_org_id
    ON org_ssr_registration_commands (org_id);

CREATE INDEX IF NOT EXISTS idx_org_ssr_reg_cmd_fetched_at
    ON org_ssr_registration_commands (fetched_at);
```

**Note**: `fetched_at` is stored as an ISO-8601 UTC string (`YYYY-MM-DDTHH:MM:SSZ`) --
SQLite has no native timestamp type and MistHelper's convention across other tables is
text-encoded ISO-8601.

## `ENDPOINT_PRIMARY_KEY_STRATEGIES` Registration

Add the following entry to the `ENDPOINT_PRIMARY_KEY_STRATEGIES` dictionary in
`MistHelper.py` (currently near line ~1672 per the copilot instructions):

```python
'getOrgSsrRegistrationCommands': {                                        # SSR adoption command fetch endpoint
    'type': 'auto_increment_with_unique',                                 # No stable server-side ID -- use client surrogate
    'primary_key': ['misthelper_internal_id'],                            # Surrogate PK generated by SQLite
    'unique_constraint': ['org_id', 'registration_code', 'fetched_at'],   # Prevent exact duplicate imports
    'indexes': ['org_id', 'fetched_at'],                                  # Common lookup axes for audit review
},
```

Each executable line carries an inline comment explaining *why* the value is what it is
(Constitution Principle VI).

## Related Data-Model Notes

- The endpoint has no relationship to the `sites`, `devices`, or `inventory` tables in
  the sense of a foreign key -- the returned command is org-scoped and generates *new*
  device rows only after the operator actually runs it on an SSR.
- If a future spec adds the paired write endpoints for SSR onboarding (`POST` claim /
  `PUT` config), those operations will produce `devices` rows that reference this
  `org_id` naturally; no schema change is needed on the current table to support that
  future relationship.

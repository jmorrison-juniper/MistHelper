# Implementation Plan: Decompose Next 5 High-Complexity Functions (Ranks 6-10)

## Summary

Refactor the next five highest-complexity functions in `MistHelper.py` into cohesive modules under `src/` while preserving operator behavior, menu compatibility, and side effects. The implementation will use a facade-preserving strangler strategy: each `MistHelper.py` entrypoint remains callable and stable, while branch-heavy logic migrates into semantically named classes with explicit responsibilities, parity tests, and complexity gates. This wave explicitly enforces inline-comment and action-logging requirements for all touched blocks.

## Architecture & Module Boundaries

### Boundary A: Multi-AP scan orchestration (`_start_site_scan_capture_all_aps`)

- **New module**: `src/capture/multi_ap_scan_workflow.py`
- **Primary class**: `MultiApScanCaptureWorkflow`
- **Responsibilities**:
  - AP inventory retrieval and normalization
  - capture parameter collection/validation
  - single-payload `aps` map construction
  - execution/result handling handoff to existing capture manager components
- **Compatibility**: `MistHelper.py` entrypoint delegates while preserving prompt text/order.

### Boundary B: Site PCAP wait/download state machine (`_wait_and_download_pcap`)

- **New module**: `src/capture/site_pcap_wait_download_workflow.py`
- **Primary class**: `SitePcapWaitDownloadWorkflow`
- **Responsibilities**:
  - capture completion polling
  - readiness retries/backoff windows
  - download URL retrieval and file persistence orchestration
  - result messaging and exception-safe completion paths
- **Compatibility**: Existing site capture callers continue invoking same facade signature.

### Boundary C: Org PCAP wait/download state machine (`_wait_and_download_pcap_org`)

- **New module**: `src/capture/org_pcap_wait_download_workflow.py`
- **Primary class**: `OrgPcapWaitDownloadWorkflow`
- **Responsibilities**:
  - org-level capture completion polling and readiness checks
  - download semantics mirroring site flow where behavior must match
  - org-specific API query/selection handling
- **Compatibility**: org capture flow signatures and print/log semantics preserved.

### Boundary D: Wi-Fi client export orchestration (`wifi_clients`)

- **New module**: `src/export/wifi_clients_exporter.py`
- **Primary class**: `WifiClientsExporter`
- **Responsibilities**:
  - site/client retrieval orchestration
  - filtering/normalization and row shaping
  - `DataExporter` write orchestration and parity-preserving output schema
  - progress and failure handling with action logs
- **Compatibility**: static entrypoint in `MistHelper.py` remains callable with existing optional `site_id` behavior.

### Boundary E: Interactive diagnostics/test orchestration (`run_interactive_test`)

- **New module**: `src/troubleshooting/interactive_test_runner.py`
- **Primary class**: `InteractiveTestRunner`
- **Responsibilities**:
  - prompt flow and selection control
  - input validation/safe exits
  - dispatch to test actions with consistent user messaging
  - consolidated success/failure observability
- **Compatibility**: global function in `MistHelper.py` remains entrypoint with delegated execution.

## Migration Strategy from `MistHelper.py`

Migration model: **incremental strangler with compatibility facades**.

1. **Baseline capture**: record complexity and behavior baselines for the five targets.
2. **Introduce extracted module classes** with no menu wiring changes.
3. **Delegate from `MistHelper.py` entrypoints** to new classes, preserving signatures and call sites.
4. **Parity-verify each target independently** (prompts, outputs, side effects, failure paths).
5. **Reduce entrypoint CC to <=10** by removing embedded branch-heavy logic after parity is proven.
6. **Finalize and lock gates** (VC-001..VC-007, plus explicit inline-comment/action-logging audit in touched blocks).

Rollback strategy:

- Keep facade methods in `MistHelper.py` throughout the wave.
- If any parity regression appears, temporarily route that one facade back to prior logic while keeping other migrated targets intact.
- Do not remove compatibility entrypoints in this wave.

## Implementation Constraints (Non-Negotiable)

1. **Inline comments**: Every executable touched line must include a meaningful same-line inline comment that explains intent.
2. **Action logging**: Every meaningful action in touched blocks must log before (`logging.info`) and after (`logging.debug`), with `logging.error(..., exc_info=True)` on exceptions.
3. **No thin wrappers**: Extracted classes must own logic and policy decisions, not only pass-through delegation.
4. **Safety-first input**: Interactive/destructive flows must preserve `safe_input` behavior and early-return semantics on invalid confirmation/input.
5. **Backward compatibility**: Existing menu IDs, invocation patterns, and user-visible operational flow must remain stable.

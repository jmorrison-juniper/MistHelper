**Plan**: [plan.md](./plan.md)

This document resolves the unknowns required before design and implementation. Each task

## Research Task 1: SDK function signature and behavior

**Source consulted**: `documentation/api/sites/GET_sites_site_id_webhooks_webhook_id_events_count.md`
(enriched OpenAPI doc).

**Decision**:
Invoke the endpoint via the mistapi SDK using the canonical URL-derived module path:

```python
mistapi.api.v1.sites.webhooks.events.count.countSiteWebhooksDeliveries(
    apisession,
    site_id,
    webhook_id,
    error=None,
    status_code=None,
    status=None,
    topic=None,
    distinct=None,
    start=None,
    end=None,
    duration="1d",
    limit=100,
)
```

The SDK returns a `mistapi.APIResponse` whose `.data` attribute is the parsed JSON body.
The body is a single JSON object (the count envelope), keyed as follows per the enriched
doc:

- `distinct` (string) -- the field over which the count was bucketed (echoes the request).
- `start` (int32 epoch seconds) -- start of the count window.
- `end` (int32 epoch seconds) -- end of the count window.
- `limit` (int32) -- per-bucket cap echo.
- `total` (int32) -- total deliveries in window before bucketing.
- `results` (unique array of `count_result` objects) -- bucket rows. Each bucket has at
  minimum `count: int32` and may carry additional string properties whose key is the
  value of `distinct` (for example, when `distinct=topic` each bucket carries a
  `topic: "alarms"` style key).

Path parameters required by the SDK: `site_id` (UUID), `webhook_id` (UUID).
Query parameters are all optional. Pagination is supported via `limit` (and `page` when
present on the SDK -- not all generated mistapi modules expose `page` for `count`
endpoints because the result-set size is governed by the bucket cardinality, not row
count).

**Rationale**:
The enriched per-endpoint doc lists the SDK module as
`mistapi.api.v1.sites.webhooks.countSiteWebhooksDeliveries()`, but the spec.md (the
authoritative feature contract) and the OpenAPI URL both place the function under the
`events.count` sub-path. The mistapi SDK historically generates module paths from the URL
not the tag, verified against adjacent endpoints (for example
`GET /api/v1/sites/{site_id}/webhooks/{webhook_id}/events/search` lives under
`mistapi.api.v1.sites.webhooks.events.search`). We therefore follow the spec / URL
mapping. Final verification happens at implementation time via:

```powershell
python -c "from mistapi.api.v1.sites.webhooks.events import count; help(count)"
```

If `count` is not present at that path in the installed `mistapi` version, the fall-back
import is `from mistapi.api.v1.sites.webhooks import count_site_webhooks_deliveries`
(snake-cased synonym sometimes generated by mistapi). Either way, the public function
name remains `countSiteWebhooksDeliveries`.

**Alternatives Considered**:

1. *Direct `requests.get` against the URL.* Rejected -- the constitution forbids direct
   HTTP when a mistapi method exists.
2. *Use the path implied by the doc (`...sites.webhooks.countSiteWebhooksDeliveries`).*
   Rejected -- the SDK organizes modules by URL, not by OpenAPI tag; the spec.md
   explicitly names the URL-based module path. The doc string is treated as a soft hint,
   not a binding source.

## Research Task 2: Primary Key Strategy

**Decision**:
Use a **composite primary key** strategy on two separate output tables.

- `site_webhook_deliveries_count_summary`: PK =
  `(site_id, webhook_id, distinct, start, end, status, status_code, error, topic)` --
  one row per (site, webhook, query window, filter combination). The PK includes every
  filter knob because two different filter combinations against the same window are two
  distinct logical queries that both need to be retained.
- `site_webhook_deliveries_count_buckets`: PK =
  `(site_id, webhook_id, distinct, start, end, bucket_value)` -- one row per bucket in
  the `results` array. `bucket_value` is the value of the `distinct` key inside each
  bucket object (for example `bucket_value="alarms"` when `distinct=topic`); when
  `distinct` is omitted by the caller, MistHelper uses the literal string `"_overall"`
  to keep the PK populated.

Both entries register in `ENDPOINT_PRIMARY_KEY_STRATEGIES` with type `composite_pk`.
`site_id` and `webhook_id` are injected by MistHelper from the prompt values before the
upsert; Mist does not return them in the body. `INSERT OR REPLACE` semantics ensure
re-polling the same window updates the previously stored snapshot.

**Rationale**:
The endpoint returns *current* aggregate counts for a sliding window. Re-running the
menu item against the same site/webhook/window must update the existing rows, not append
duplicates. The natural identifier of a snapshot is the full `(site, webhook, query
parameters)` tuple because that tuple is what the Mist API resolves the count against.
Splitting the envelope from the bucket array lets a user query the per-bucket counts
without unpacking JSON, and lets the summary row carry the `total` and `limit` echoes
that are scalar and would be wasteful to duplicate on every bucket row.

**Alternatives Considered**:

1. *`auto_increment_with_unique`.* Rejected -- repeated polls would accumulate duplicate
   snapshots, defeating the upsert behavior the spec requires.
2. *Single combined table with one row per bucket and the envelope fields duplicated.*
   Rejected -- denormalizes `total/limit`, wastes storage, and complicates queries that
   only want the envelope.
3. *Hash the query parameters into a single `query_hash` PK column.* Rejected -- opaque
   hashes are unfriendly to junior NOC operators reading the SQLite directly; the
   explicit composite key documents the snapshot identity at a glance.

## Research Task 3: Output filename and SQLite table

**Decision**:

- CSV (summary): `data/site_<site_id_short>_webhook_<webhook_id_short>_count_summary.csv`
- CSV (buckets): `data/site_<site_id_short>_webhook_<webhook_id_short>_count_buckets.csv`
- SQLite tables: `site_webhook_deliveries_count_summary` and
  `site_webhook_deliveries_count_buckets`
- `site_id_short` / `webhook_id_short` are the first 8 hex characters of the respective
  UUIDs -- the convention already used by adjacent site exports to avoid leaking full
  UUIDs into shell history.

The `api_function_name` argument passed to `DataExporter.write_with_format_selection()`
is `"countSiteWebhooksDeliveries"` for the summary table and
`"countSiteWebhooksDeliveriesBuckets"` (MistHelper-internal sub-table key) for the
bucket table. Both keys appear in `ENDPOINT_PRIMARY_KEY_STRATEGIES`.

**Rationale**:
Matches the naming pattern of other site-scoped exports (site UUID short prefix in the
filename, full operationId in `api_function_name`). Two output files / two SQLite tables
keep the schema clean and let a user query the bucket distribution without joining when
they don't need the envelope, and vice versa. The MistHelper-internal `...Buckets` key
mirrors the pattern used by the reference plan (spec 500) for response sub-arrays that
the Mist API does not assign an operationId to.

**Alternatives Considered**:

1. *Single output file with JSON-encoded `results` column.* Rejected -- breaks SQL
   queryability and conflicts with the flattening convention used everywhere else in
   MistHelper.
2. *Full site and webhook UUIDs in the filename.* Rejected -- the resulting filename
   would exceed 80 characters and leak both UUIDs into shell history / `ls` output. The
   short prefix is enough to disambiguate locally.

## Research Task 4: Menu category placement and next available menu number

**Decision**:
Register the new operation as **menu number 86**, inside the Stats sub-cluster (80-91)
of the Interactive Safe range (60-96). Category label: "Interactive Safe -- Stats /
Webhooks".

**Rationale**:
The constitution and `.github/copilot-instructions.md` describe the menu ranges as:
1-59 Safe Org Exports, 60-96 Interactive Safe (Site devices 60-72, Insights 73-79,
**Stats 80-91**, Viewers 92-96), 97-101 + 153 Resource Intensive, 102-123 WebSocket,
124-152 Interactive, 154-194 Destructive. The endpoint is:

- **Read-only**: no destructive side effect -- excludes 154-194.
- **Site-scoped with required interactive inputs (site_id + webhook_id)**: belongs in
  60-96, not 1-59.
- **An aggregate count** producing summary stats: best fit is the Stats sub-cluster
  80-91.
- **Light-weight**: single GET, bounded by `limit=100` default -- belongs outside
  Resource Intensive (97-101) and outside Continuous Monitoring (151-152).

Number 86 is the next free integer in the Stats sub-cluster after the existing slots are
mapped out. At `/speckit.tasks` time MistHelper.py is grep'd for the latest allocated
integer; if 86 collides with an in-flight feature branch the number is shifted forward
in the same sub-cluster.

**Alternatives Considered**:

1. *Slot inside Resource Intensive (97-101).* Rejected -- this is a small, bounded GET;
   it does not exhibit the long-running or large-payload characteristics that define the
   Resource Intensive band.
2. *Append at the end (e.g., 195).* Rejected -- placing a safe read above the
   destructive cluster mis-signals risk to a junior NOC engineer scrolling the menu.
3. *Slot inside Viewers (92-96).* Rejected -- the Viewer sub-cluster is for live display
   loops, not for one-shot data extraction. Stats is the correct semantic home.

## Research Task 5: Required user prompts

**Decision**:
The new menu method asks the user for the following values via `safe_input()`. Required
prompts are always asked; optional prompts default to `None` (empty string accepts the
default).

**Required prompts:**

1. `site_id` -- prompt: `"Site ID (UUID): "`, context:
   `"site_webhook_count:site_id"`. Default: the value of `MIST_SITE_ID` in `.env` if
   present (Enter accepts). Validated via `is_valid_uuid()`; on failure log `WARNING`
   and return early.
2. `webhook_id` -- prompt: `"Webhook ID (UUID): "`, context:
   `"site_webhook_count:webhook_id"`. Default: the value of `MIST_WEBHOOK_ID` in `.env`
   if present. Validated via `is_valid_uuid()`; on failure log `WARNING` and return
   early.

**Optional prompts** (Enter to skip; value forwarded to the SDK only when non-empty):

3. `distinct` -- prompt: `"Group by field (distinct, blank for none): "`, context:
   `"site_webhook_count:distinct"`.
4. `topic` -- prompt: `"Topic filter (alarms|audits|device-updowns|occupancy-alerts|ping, blank for all): "`,
   context: `"site_webhook_count:topic"`.
5. `status` -- prompt: `"Status filter (blank for all): "`, context:
   `"site_webhook_count:status"`.
6. `status_code` -- prompt: `"Status-code filter (integer, blank for all): "`,
   context: `"site_webhook_count:status_code"`. Cast to int when non-blank.
7. `error` -- prompt: `"Error substring filter (blank for all): "`, context:
   `"site_webhook_count:error"`.
8. `duration` -- prompt: `"Window duration (e.g. 1d, 7d, 2w; default 1d): "`, context:
   `"site_webhook_count:duration"`. Default: `1d` (matches API default).
9. `limit` -- prompt: `"Bucket limit (integer, default 100): "`, context:
   `"site_webhook_count:limit"`. Default: `100`. Cast to int when non-blank.

`start` and `end` are not prompted directly because `duration` is the operator-friendly
substitute exposed by the Mist API; an advanced user can still set explicit epochs by
overriding via environment variables (`MIST_WEBHOOK_COUNT_START`,
`MIST_WEBHOOK_COUNT_END`).

`.env` values used (loaded via the existing `python-dotenv` bootstrap, never logged):

- `MIST_HOST` -- required by `mistapi.APISession`.
- `MIST_API_TOKEN` -- required by `mistapi.APISession`.
- `MIST_SITE_ID` -- optional default for prompt 1.
- `MIST_WEBHOOK_ID` -- optional default for prompt 2.
- `MIST_WEBHOOK_COUNT_START`, `MIST_WEBHOOK_COUNT_END` -- optional epoch overrides.

**Rationale**:
Two UUIDs are non-negotiable inputs because the Mist endpoint requires both path
parameters. Every other parameter is genuinely optional on the API, so each is
surfaced as an optional prompt with a default of `None` (skip). Defaults for `duration`
and `limit` mirror the API defaults so an operator who presses Enter through every
optional prompt still gets a valid call. Reading `start`/`end` from environment
variables instead of prompts keeps the interactive UX short (nine prompts is already
the upper bound the constitution tolerates before screen-fatigue sets in).

**Alternatives Considered**:

1. *Always request every filter value.* Rejected -- forces ten interactive prompts on
   every run and confuses junior operators who only want the default 1-day total.
2. *Hard-code `distinct=topic` to remove a prompt.* Rejected -- the choice of bucket
   field is operationally meaningful (topic vs status vs status_code answer different
   questions); the user must drive it.
3. *Prompt for `start` and `end` directly.* Rejected -- epoch seconds are unfriendly to
   interactive entry; `duration` is the documented operator-friendly knob.

# Phase 0 Research: getOrgAlarmTemplate

**Spec**: [spec.md](./spec.md)
**Plan**: [plan.md](./plan.md)
**Date**: 2026-06-29

This document resolves the unknowns required before design and implementation. Each
task follows the Decision / Rationale / Alternatives Considered format.

## Research Task 1: SDK function signature and behavior

**Source consulted**:
`documentation/api/orgs/GET_orgs_org_id_alarmtemplates_alarmtemplate_id.md`
(enriched OpenAPI doc).

**Decision**:
Invoke the endpoint via the mistapi SDK at
`mistapi.api.v1.orgs.alarmtemplates.getOrgAlarmTemplate(apisession, org_id,
alarmtemplate_id)`. The SDK returns a `mistapi.APIResponse` object whose `.data`
attribute is the parsed JSON body. The body is a single JSON object (not a list, not
paginated) with the following top-level keys per the doc:

- `id` (string UUID, read-only) -- unique template identifier.
- `org_id` (string UUID, read-only) -- owning organization.
- `name` (string) -- human-readable template name (example: `"default"`).
- `created_time` (number, epoch seconds, read-only).
- `modified_time` (number, epoch seconds, read-only).
- `delivery` (object, **required**) -- top-level email-delivery config with keys
  `additional_emails` (string[]), `enabled` (bool), `to_org_admins` (bool),
  `to_site_admins` (bool).
- `rules` (object, **required**) -- a dynamic-key map where each property name is an
  alarm-key string (for example `"ap_offline"`, `"bad_cable"`) and the value is an
  `alarm_template_rule` object with `enabled` (bool) plus an optional per-rule
  `delivery` object whose shape is identical to the top-level `delivery` object.

Required path parameters: `org_id` (UUID), `alarmtemplate_id` (UUID). No query
parameters. No request body. Non-paginated.

**Rationale**:
The spec.md explicitly names the SDK module as
`mistapi.api.v1.orgs.alarmtemplates`. The enriched per-endpoint doc shows
`mistapi.api.v1.orgs.alarm_templates.getOrgAlarmTemplate()` (with an underscore),
but the mistapi SDK historically generates module paths from the OpenAPI URL path
segments without inserting underscores (verified by inspecting the adjacent
`listOrgAlarmTemplates` operation, whose URL is `/orgs/{org_id}/alarmtemplates`
and whose module is `mistapi.api.v1.orgs.alarmtemplates`). The spec.md is the
authoritative feature contract; we follow it. Final verification happens at
implementation time via
`python -c "from mistapi.api.v1.orgs import alarmtemplates; help(alarmtemplates)"`
inside the venv.

**Alternatives Considered**:

1. *Direct `requests.get` against
   `https://{host}/api/v1/orgs/{org_id}/alarmtemplates/{alarmtemplate_id}`.*
   Rejected -- the constitution forbids direct HTTP when a mistapi method exists.
2. *Use the underscored module path from the enriched doc
   (`...orgs.alarm_templates...`).* Rejected -- the SDK organizes modules by URL
   path segment (no underscore in the URL), and the spec.md names the
   non-underscored path. The doc's underscore is a generator artifact.
3. *Use the list endpoint `listOrgAlarmTemplates` and filter client-side by
   `alarmtemplate_id`.* Rejected -- wastes API budget, and the spec's User Story
   is explicitly for the single-template GET.

## Research Task 2: Primary Key Strategy

**Decision**:
Use a **natural primary key** for the parent template and a **composite primary
key** for the per-rule sub-table:

- `org_alarm_templates`: PK = `id` (the Mist-provided UUID). One row per alarm
  template per org. Strategy type: `natural_pk`.
- `org_alarm_template_rules`: PK = `(alarmtemplate_id, rule_name)`. One row per
  alarm key inside the template's `rules` map. Strategy type: `composite_pk`.

The `ENDPOINT_PRIMARY_KEY_STRATEGIES` registration declares two entries: the
operationId `getOrgAlarmTemplate` for the parent rows, and the MistHelper-internal
key `getOrgAlarmTemplateRules` for the flattened child rows. `org_id` is injected
into both row sets by MistHelper before the upsert (the API does return `org_id` in
the parent body; MistHelper still validates it matches the request path).

**Rationale**:
The endpoint returns one fully-formed `Alarm Template` object whose `id` is a
stable UUID generated by Mist at template creation time and never changes. That
satisfies the `natural_pk` criterion exactly. The nested `rules` object is a
dynamic-key map; the only stable identifier per rule is the alarm-key string
itself, which is unique within a single template. Pairing `alarmtemplate_id` with
`rule_name` produces a globally unique composite key that survives template
renames and re-runs. `INSERT OR REPLACE` upserts both tables cleanly on every
poll.

**Alternatives Considered**:

1. *`auto_increment_with_unique` on both tables.* Rejected -- the spec's
   Acceptance Scenario 3 explicitly requires repeated runs to upsert without
   duplicates; an auto-increment surrogate would create a new row every poll.
2. *Single combined table with rules stored as a JSON-encoded blob column.*
   Rejected -- breaks SQL queryability and contradicts the flattening
   convention used everywhere else in MistHelper.
3. *`composite_pk` on `(org_id, id)` for the parent.* Rejected -- Mist
   guarantees template `id` is globally unique across orgs (it is a v4 UUID), so
   `org_id` is redundant in the parent PK. `org_id` is kept as an indexed FK
   instead.

## Research Task 3: Output filename and SQLite table

**Decision**:

- CSV (parent): `data/org_<org_id_short>_alarm_template_<alarmtemplate_id_short>.csv`
- CSV (rules):
  `data/org_<org_id_short>_alarm_template_<alarmtemplate_id_short>_rules.csv`
- SQLite tables: `org_alarm_templates` (one row per template, keyed by `id`) and
  `org_alarm_template_rules` (one row per (template_id, rule_name)).
- `org_id_short` and `alarmtemplate_id_short` are each the first 8 hex characters
  of the respective UUID -- the convention used by adjacent template exports in
  MistHelper for human-readable filenames without leaking full UUIDs into shell
  history.

The `api_function_name` argument passed to
`DataExporter.write_with_format_selection()` is `"getOrgAlarmTemplate"` for the
parent and `"getOrgAlarmTemplateRules"` for the rules child. `DataExporter` uses
each string as the lookup key into `ENDPOINT_PRIMARY_KEY_STRATEGIES`.

**Rationale**:
Matches the naming pattern used by `listOrgAlarmTemplates` (parent table
`org_alarm_templates`). Two output files / two SQLite tables keeps the schema
clean and lets a user query a template's top-level delivery config without
joining when per-rule detail is not needed. The single-template GET feeds the
same parent table as the list endpoint, so the existing
`listOrgAlarmTemplates` rows and this single-template GET rows upsert into one
canonical `org_alarm_templates` table by `id` -- no schema divergence.

**Alternatives Considered**:

1. *One row per call with rules collapsed to a JSON-encoded column.* Rejected
   -- breaks downstream SQL filtering on rule enablement state.
2. *Full UUIDs in CSV filenames.* Rejected -- leaks UUIDs into shell history /
   `ls` output. Short form is enough to disambiguate locally.
3. *Reuse the existing `listOrgAlarmTemplates` output filename exactly.*
   Rejected -- conflates "all templates for an org" output with
   "one specific template" output. The disambiguating
   `<alarmtemplate_id_short>` segment in the filename makes both coexist
   cleanly under `data/`.

## Research Task 4: Menu category placement and next available menu number

**Decision**:
Register the new operation as **menu number 38**, sitting inside the Safe Org
Exports cluster between operations 37 and 41 (the Templates sub-cluster) and
adjacent to the existing `listOrgAlarmTemplates` menu entry. The category label
is "Safe Org Exports -- Templates".

**Rationale**:
The constitution and `.github/copilot-instructions.md` describe the menu ranges
as: 1-7 Sites, 8-14 Inventory, 15-19 Device stats, 20-26 Events, 27-30 Clients,
31-36 Gateways, **37-41 Templates**, 42-50 Config/Admin, ..., 154-194
Destructive. The enriched per-endpoint doc lists
`listOrgAlarmTemplates` as menu 35 (in the gateways block) which contradicts
the cluster boundaries; that is interpreted as a stale doc note rather than the
authoritative source. The authoritative menu allocation is verified by grep at
`/speckit.tasks` time. **38** is the first contiguous integer in the Templates
cluster that is most likely free; if the implementation pass finds 38 already
allocated, the next free integer inside 37-41 is used. Either way the new menu
sits in the same Templates safe-export cluster.

**Alternatives Considered**:

1. *Append to the end (e.g., 195).* Rejected -- the destructive cluster ends at
   194, and placing a read-only template GET above the destructive block
   mis-signals risk to a junior NOC engineer scrolling the menu.
2. *Slot inside Resource Intensive (96-101).* Rejected -- this endpoint is a
   single GET that returns one small JSON object, no pagination, no long-running
   work. It belongs in the safe Templates block.
3. *Replace the existing `listOrgAlarmTemplates` menu item.* Rejected -- the
   list endpoint is still a distinct user-facing capability (enumerate all
   templates without knowing IDs); both endpoints should coexist.

## Research Task 5: Required user prompts

**Decision**:
The new menu method asks the user for **exactly two** values via `safe_input()`:

1. `org_id` -- prompt: `"Org ID (UUID): "`, context:
   `"org_alarm_template:org_id"`. Default: the value of `MIST_ORG_ID` in `.env`
   if present (pressing Enter accepts the default). Validated via the existing
   `is_valid_uuid()` helper before the API call; on failure, log `WARNING` and
   return early.
2. `alarmtemplate_id` -- prompt: `"Alarm Template ID (UUID): "`, context:
   `"org_alarm_template:alarmtemplate_id"`. No `.env` default (template UUIDs
   are not typically pinned in environment files; the user runs
   `listOrgAlarmTemplates` first to discover IDs). Validated via the same
   `is_valid_uuid()` helper. On invalid input, log `WARNING` and return early.

`.env` values used (loaded via the existing `python-dotenv` bootstrap, never
logged):

- `MIST_HOST` (e.g., `api.mist.com`) -- required by `mistapi.APISession`.
- `MIST_API_TOKEN` -- required by `mistapi.APISession`.
- `MIST_ORG_ID` -- optional default for prompt 1.

**Rationale**:
The endpoint's two required path parameters are exactly these two UUIDs. The
endpoint has zero query parameters and no request body, so two prompts is the
complete and minimal input surface. Keeping `alarmtemplate_id` un-defaulted in
`.env` matches existing MistHelper convention for per-object IDs that change
between runs (UUIDs of single records are not stable environment configuration).

**Alternatives Considered**:

1. *Auto-discover all alarm templates and let the user pick from a numbered
   list.* Rejected for this Phase 0 design -- adds a hidden second API call
   (`listOrgAlarmTemplates`) before every run, doubling the rate-limit cost
   and complicating the `--menu 38` non-interactive path. Could be added later
   as a separate enhancement.
2. *Accept the IDs as CLI flags (`--org-id`, `--alarmtemplate-id`).* Rejected
   for this spec -- the entire MistHelper menu system is prompt-driven; adding
   flags here without doing it for every menu item creates inconsistency.
   `--menu 38` plus the `safe_input()` defaults already supports the
   non-interactive smoke path.
3. *Add an output-filename override prompt.* Rejected -- adds keystrokes
   without operational value. The deterministic filename scheme from Research
   Task 3 makes results easy to find under `data/`.
